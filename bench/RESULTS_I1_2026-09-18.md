# I1: bulk-ingest bloat -- root cause found, fixed, and two deadlocks found on the way

**Date:** 2026-09-18 · **Host:** r6id.4xlarge, PG 17.10, local NVMe
**Raw:** `bench/data_i1_2026-09-18/`
**Supersedes** the mechanism section of `RESULTS_KNOWN_ISSUES_2026-09-14.md`, which was
half right.

## Result

Field shape (40k base docs at 1,660 terms/doc), then **30,000 more documents as
row-per-transaction ingest with autovacuum on and no manual maintenance**:

| | v1.8.2 | this branch |
|---|---|---|
| baseline | 1,823 MB | 1,823 MB |
| +5k rows | 4,975 MB | 1,823 MB |
| +10k rows | 8,383 MB | 1,823 MB |
| +15k rows | **deadlocked** | 1,832 MB |
| +20k / +25k / +30k | -- | 1,831 / 1,823 / **1,823 MB** |
| parity vs regex | -- | 84 = 84 |
| after one `fts_vacuum` | -- | 863 MB |

**Zero net growth over 30,000 documents.** v1.8.2 grew 3.2 GB per 5,000 and then hung.

The index "breathes" by ~9 MB and returns to baseline; `fts_vacuum` shows the live data is
~863 MB, so the resident size holds at ~2.1x live under sustained ingest -- a steady-state
free pool, not accumulation. **The requirement -- bounded, online, no operator
scheduling -- is met on this shape.**

## How the cause was found: one falsified prediction, then two measured facts

**Theory #5 (the XID stamp is too pessimistic) was killed by prior art before any code.**
`bm25_free_page` stamps freed pages with `ReadNextTransactionId()`; I suspected that was
one frontier too new. nbtree's `_bt_unlink_halfdead_page` does exactly the same
(`safexid = ReadNextFullTransactionId()`) and its comment explains why it is tight enough.
Dropped.

**Theory #6 (the merge runs inside a long multi-row statement, so the freeing xid is the
oldest snapshot) made a falsifiable prediction:** 2,000 docs as one statement vs 2,000
single-row transactions should differ "several times". Measured:

```
bulk   (1 statement) : 49.2 pages/doc -> 8 MB after fts_vacuum
single (2000 txns)   : 34.3 pages/doc -> 8 MB after fts_vacuum
```

Only 1.4x apart, and **both ~70-100x their compacted size**. The horizon was not the
binding constraint. Falsified.

**What the data pointed at instead:** if a fresh transaction per row still cannot reuse
pages, reuse is not being *attempted*. `bm25_merge_segments` entered
`BM25_ALLOC_EXTEND_ONLY` for its whole loop. Extend-only never consults the free list --
not for pages freed by *this* call (the hazard it guards) and not for pages freed by
*previous* calls (safe, and the vast majority). At 1,660 terms/doc every document mints
a segment and triggers a merge, so the merge was the dominant writer and its freed pages
were reachable only by `fts_vacuum`.

## The fix: make the guard exact instead of conservative

`BM25_ALLOC_SNAPSHOT`: gather the free list **once at scope entry, before this call frees
anything**, hand out only from that snapshot, then extend, and **never re-consult the live
FSM**. A page freed by merge N in this loop cannot reach merge N+1 -- it is not in the
snapshot -- so the recycle-race guard holds by construction. Pages from earlier calls are
in the snapshot and are reused.

Measured on the 2,000-doc probe: single-txn **34.3 -> 3.0 pages/doc** (11.4x); bulk
statement unchanged at 49.2 (predicted: inside one statement the freeing xid *is* the
horizon, and nothing allocation-side changes that -- see "still open").

## Two deadlocks the fix exposed -- both pre-existing

Running the fix at field shape hung at row 680 of round 3. Two distinct bugs, each
isolated with `gdb` on the live backends, each with a stack that named it.

**1. The insert path's full-directory merge ran without the maintenance mutex.**
`bm25_add_segment_with_room()` -- "directory is at the 128 cap, merge to make room" -- was
the only merger in the tree that did not take `bm25_maintenance_lock`. It ran concurrently
with autovacuum's merge on the same index. Under extend-only the two never touched the same
block (merely wasteful). Under SNAPSHOT both snapshotted the same free list, handed out the
same block, and deadlocked on its buffer lock.

**Confirmed pre-existing: v1.8.2 deadlocks the same way on the same harness at row 1,674,
with no other change.** This has shipped in every release with an insert-path
full-directory merge; it needed autovacuum to be merging at the moment the directory
filled, which is exactly what high-terms-per-doc ingest produces.

Fixed by taking the mutex (blocking, correctly: the insert must make room or fail). And
**enforced**: `bm25_merge_segments` and `bm25_merge_all` now `elog(ERROR)` if entered
without the mutex or an AccessExclusiveLock. That check immediately caught a second
unprotected site -- `bm25_build_finalize` under CREATE INDEX CONCURRENTLY, which holds only
ShareUpdateExclusiveLock -- now also under the mutex.

**2. `bm25_page_recyclable` treated an un-flagged page as free.**
```c
if (!(op->flags & BM25_FREED))
    return true;   /* not gated (older free, or in-use race) */
```
The comment names the case. Instrumented handout logging caught it live:
`handout-LIVE blk=65 flags=0x4 nextblk=66` -- a **live posting page, mid-chain**, in the
snapshot free list (the FSM records free *space*, not liveness; a partially filled live
page qualifies), handed out as merge output while the same merge held it pinned as input.
Self-deadlock on its own buffer.

Fixed: no `BM25_FREED` flag => **not** recyclable, checked before the AccessExclusiveLock
bypass too. Cost: pages freed by a build predating the flag are reclaimed only by tail
truncation, not reuse. Safety over that corner.

## Regression test, proven to discriminate

`t/007_segment_cap.pl` now runs a repeated `VACUUM` concurrently with its four inserters
filling the directory, with a 300 s deadline (IPC::Run's `finish` has none). Verified
**red on v1.8.2's `pg_fts_am.c`** (`HUNG ... 300.386s`) and **green on the fix**, with the
harness restored between runs. Two harness bugs fixed on the way: pumping one IPC::Run
handle at a time starved the others (looked exactly like the deadlock, on the fixed code,
until the wait events said `ClientRead`); and psql fed from a scalar needs an explicit
`\q` or `pumpable` never goes false.

## Still open: the single-large-statement shape

`INSERT ... SELECT ... generate_series(1, N)` for oversized rows still shows ~49 pages/doc
until `fts_vacuum`. Inside one statement the freeing xid is the oldest snapshot, so no page
freed during it can pass the horizon until it ends -- no allocation policy changes that.
Modelled the alternative (raise the merge threshold inside a long statement to do fewer,
larger merges): leveled merge already amortises to `log_F(N)` rewrites per doc, so going
F=8 -> 64 is ~2x, not the 8x it looks like. Recorded as the residual; `fts_vacuum` after a
bulk load remains the guidance for that one shape, and it is fast (tens of seconds).

## nseg spike, noted honestly

Round 3 showed `nseg=92`. That is the mutex fix working: the insert path now blocks behind
autovacuum's merge instead of racing it, so segments queue until the merge finishes, then
collapse (92 -> 73 -> 14 -> 12). Bounded under the 128 cap and self-correcting. The
alternative was the deadlock.

## M3 (longer ingest), same box, same fixed build

20 rounds x 5,000 row-per-transaction inserts (100,000 documents), autovacuum on, no manual
maintenance. Raw: `data_i1_2026-09-18/m3.log`.

| | |
|---|---|
| size, start -> end | 1,823 MB -> **1,875 MB** (+52 MB over 100k docs) |
| largest transient | 2,284 MB in round 18, back to 1,875 the next round |
| `fts_vacuum` at the end | 1,875 -> **1,875 MB: nothing reclaimable** |
| parity vs regex | 169 = 169 |
| segments | 7-23, settling at 8 |

**The resident size at the end IS the live size.** There is no free pool left over, which
is a stronger result than the 6-round run's ~2.1x.

**A per-document ratio would be wrong here, so none is given.** The baseline 1,823 MB is a
multi-segment build (`maintenance_work_mem = 256MB`) that `fts_vacuum` compacts to ~863 MB;
and the churn generator reuses the build's fixed vocabulary, so churn documents cost far
less dictionary than build documents. The honest statement is the one in the table: +52 MB
net over 100k documents, with nothing left to reclaim.

**Throughput does not decay; it oscillates.** Per-round rates were 33-56 rows/s across all
20 rounds, and the round durations are exactly 90 / 120 / 150 s -- 1x, 1.33x, 1.67x a 90 s
floor -- i.e. whether an autovacuum cycle landed inside the round. The C2 question ("does
the 41% decay level off?") is answered for this shape: there is no decay to level off, only
cycle noise. The absolute rate is the **harness** (psql building a 1,660-term string per
row via `generate_series`), not the index, and is not a publishable ingest figure.
