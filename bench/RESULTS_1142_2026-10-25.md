# 1.14.2: index scan returned rows whose own `@@@` is false (pg.ddx.io, 2026-10-24)

**Current.**  EC2 c6id.8xlarge (32 vCPU, 61 GB, local NVMe), Debian 13, PostgreSQL 18.6
and 17.10 built from source (`-O2 -g`, `fsync=off` for load speed).  pg_fts v1.10.0
(8bccf0c) and v1.14.1 (6a91cd7) built from their tags.  Raw outputs and every script
are in `data_1142_2026-10-25/` (`scripts/`).

## Verdict

The report (1.14.1, PG 18.6, an expression index `to_ftsdoc('english', message)` on
3.65M commit messages, insert-only importer; an index scan returns `(226563,6)`, which
matches, and `(226563,7)`, which does not, both as exact matches) **reproduces exactly
on 1.10.0, survives an in-place upgrade to 1.14.1, and is cleared by REINDEX.**
**1.14.1 did not reproduce it in any run** (below).  The bug is index data written by
<= 1.10.0: entries of rows that died while still in the pending list, which 1.10.0's
VACUUM never removed (fixed in 1.11.0, whose notes said no REINDEX was needed).
1.14.2 is therefore a documentation and safety release (CHANGELOG 1.14.2).

## 1. Minimal reproduction (`scripts/shift.sql`, `shift.out`; test `pending_reuse`)

A 400-row batch alternating `visibility map` and `hash_any` messages is inserted and
rolled back, VACUUM frees its slots, and the batch is retried without its first row, so
every retried row lands one slot below its aborted copy.

| build | truth | bitmap rows | false rows | fts_count |
|---|---|---|---|---|
| 1.10.0 | 200 | 399 | 199 | 399 |
| 1.10.0 index, upgraded in place to 1.14.1, then VACUUM + `fts_merge` | 200 | 399 | 199 | -- |
| same, after REINDEX | 200 | 200 | 0 | -- |
| 1.14.1 | 200 | 200 | 0 | 200 |
| 1.14.1 with the 1.11.0 fix removed (no `bm25_flush_pending` at the top of `bm25_bulkdelete`) | 200 | 399 | 199 | 399 |

On 1.10.0 the returned TIDs alternate `(31,119)` true, `(31,120)` false, `(31,121)`
true...: the report's pattern.  The regression test `pending_reuse`, with a stable
`id` range, gives 199 false rows on the mutant and 0 on 1.14.1
(`pending_reuse-*.out`).

## 2. How a dying pending row leaves a false entry (`scripts/mech.sql`, `mech.out`)

A committed sentinel row keeps VACUUM from truncating the dead slots; 300 dead rows,
then 300 non-matching rows reuse the slots (all 300 counted in reused slots each time).
`visibility & map`, 50 true matches:

| way the row died | 1.10.0 false rows | 1.14.1 PG18 | 1.14.1 PG17 |
|---|---|---|---|
| ROLLBACK of a batch | 199 | 0 | 0 |
| DELETE of rows still pending | 199 | 0 | 0 |
| duplicate-key error on the batch's last row | 199 | 0 | 0 |
| COPY failing at row 3,000 (after two multi-insert flushes) | 199 (fts_count 2,050) | 0 | 0 |
| INSERT ... ON CONFLICT DO NOTHING (conflicting rows) | 0 | 0 | 0 |

(A first run of the COPY case failed at row 300, inside COPY's 1,000-row buffer, so no
heap row was written and it proved nothing; the table above is the corrected run.)

bitmap scan and the plain index scan with the heap truth (`fts_match` on a materialized
`to_ftsdoc` of every row) for 10-12 terms, both directions, plus `fts_count`.

stale entry keeps producing false rows for as long as its slot keeps being reused.

## 4. Races on 1.14.1 (`scripts/race.sh`, `armR*.txt`, `raceR*-check.log`)

20 minutes each, 6 sessions issuing at random: plain inserts; insert then delete
two thirds; ROLLBACK then a retry shifted by one row; filler inserts; a COPY of 2,500
rows failing on the last; insert + delete in one transaction; ON CONFLICT DO NOTHING
+ random delete.  Against autovacuum (naptime 1 s, thresholds 50/200 rows, no cost
delay), a VACUUM every 3 s, `fts_merge` every 20 s and inline flushes.  A checker ran
every second in REPEATABLE READ, comparing index-scan count and false rows with the
heap count in the same snapshot.

| arm | PG | flush threshold | rows at end | checker snapshots | mismatching | final diff (6 terms) |
|---|---|---|---|---|---|---|
| R1 | 18.6 | 200 | 5.90M | 95 | 0 | 0 false, 0 missing |
| R2 | 18.6 | 50 | 5.87M | 93 | 0 | 0 false, 0 missing |
| R3 | 17.10 | 200 | 5.78M | 98 | 0 | 0 false, 0 missing |

The final 6-term diffs were cut short at 4-5 terms by the time box; every term
completed was 0/0 (`visibility & map`: 1,629,194 / 1,614,884 / 1,575,718 rows).

## 5. The documented check (CHANGELOG 1.14.2; `scripts/check_terms.sql`, `check-*.out`)

`SET enable_seqscan = off` and `... WHERE expr @@@ q AND NOT fts_match(expr, q)`:
the planner puts the `@@@` in the bitmap index scan and `fts_match` in the heap
filter, so it counts exactly the rows the index returns that do not match.

| index | `vacuum` | `visibility & map` | `hash & index` | `freeze` | time |
|---|---|---|---|---|---|
| C1 (1.10.0-written, upgraded) | 1,424 | 214 | 441 | 429 | 24.8 s |
| A (1.14.1) | 0 | 0 | 0 | 0 | 26.0 s |

The C1 numbers equal the full TID diff of section 3.  (Times are one run on a loaded
host, for scale only.)

## Not reproduced, not tried

- Not reproduced on 1.14.1 by anything above.  Not tried: CREATE INDEX CONCURRENTLY
  or REINDEX CONCURRENTLY during aborting inserts, a parallel build, and a standby.
- The customer's second index (`idx_ag_msg_fts`, mail headers) was not available; the
  same cause is assumed from the same history, unverified.
