3. **SHOULD-FIX (b)**, `:274` — `prs.curwords = 0` throws away the first parse's word pointers without freeing them.
   - **Leak:** each one is a lexeme string the dictionary palloc'd. They stay allocated until the calling context resets.
   - **Cost:** for a document over 16,383 tokens, lexeme memory roughly doubles and parsing runs twice (both unmeasured).
   - **Fix:** `for (i=0;i<prs.curwords;i++) pfree(prs.words[i].word);` before the reset. `to_tsany.c` already pfrees `words[i].word`, so it is safe.
   - **wpos bounds — OK:** `wpos` is only indexed below `curwords`. Either `curwords <= capwpos` already, or `capwpos` grows to `lenwords >= curwords`. It can never be indexed past `capwpos`.

4. **NIT (b)**, the comment at `:212` — "a token is at least one byte, so no ordinal inside a chunk reaches the cap" is not true for a thesaurus. A thesaurus that expands one word into several (`TSL_ADDPOS`) can produce more than 16,383 positions inside a 16,383-byte chunk. For example, `x` mapped to a four-word substitute, over 8,192 `x`s, gives 32,768 positions. They get capped exactly as before; nothing crashes. Either reword the comment, or check `prs->pos > 16383` per chunk and halve the chunk.

5. **OK, with a NIT on a comment (c)**, `:285-293`, `pg_mbcliplen` behaviour:
   - **Boundary:** on REL_17 and REL_18 it returns a length no greater than the limit that ends on a character boundary as the encoding's mblen sees it. Single-byte encodings go through `cliplen`.
   - **No overrun:** this branch only runs when more than 16,383 bytes remain, so a character that runs past the end of the text cannot read past the buffer.
   - **It can return 0:** both versions stop at a NUL byte. A text value with an embedded NUL (only possible through C code; text input rejects it) gives `lim = 0`. The `pg_mblen` fallback then advances 1 byte, so there is no infinite loop.
   - **Comment is wrong:** the fallback is reachable, so "cannot happen" should read "embedded NUL". `pg_mblen_range(str+start, str+len)` is the non-deprecated bounded form.

6. **OK (d)** — the whitespace back-off is safe in every server encoding.
   - **Server encodings** are SQL_ASCII, EUC_JP/CN/KR/TW/JIS_2004, UTF8, MULE_INTERNAL and the single-byte encodings (`PG_ENCODING_BE_LAST = KOI8U`). SJIS, BIG5, GBK, UHC, GB18030 and JOHAB are client-only.
   - **Trail bytes:** EUC and MULE trail bytes are 0xA0 or higher, and UTF-8 trail bytes are 0x80-0xBF. None can be read as an ASCII space, so the back-off always lands on a character boundary.
