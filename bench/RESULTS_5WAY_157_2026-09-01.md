# 5-way BM25 comparison — pg_fts 1.5.7 vs the field (2026-09-01)

Re-run of the August 5-way on the same real Wikipedia corpus, now with **pg_fts
1.5.7** — the first re-benchmark since 1.5.0, so it captures everything shipped
in 1.5.1–1.5.7 (doclen-sidecar fast reads, AND-recall fix, the crash fixes, the
concurrency work). It surfaced a **regression the 1.5.4 doclen-cache introduced
for rare/mid ranked** that the 1.5.0 numbers did not show — documented below.

## Rig
- EC2 r6id.4xlarge (account `bene`), Intel Xeon 8375C @ 2.90GHz, 16 vCPU, 128GB,
  local 884GB NVMe instance store, PostgreSQL 17.10, `shared_buffers=64GB`,
  prewarmed. One dedicated instance per engine (Amazon Linux 2023).
- Corpus: wikimedia/wikipedia 20231101.en, first **2,188,038** articles. This
  run indexed **title+body** (heap 3914 MB); the Aug run indexed body only
  (heap 1744 MB). df bands identical: rare=slovakia (10,875), mid=hungary
  (~24k), common=year (734,896). avgdl 485.
- Warm `\timing`, median of 5 (first run dropped). pg_fts and pg_textsearch and
  vchord are C/Rust index AMs; pg_search is Tantivy via pgrx.

## The finding: the 1.5.4 doclen-cache is a per-scan tax that cripples rare/mid ranked

The default `doclen_sidecar=on` is **10-12x slower than it should be on
rare/mid ranked** (rare 25.6 ms vs 1.6 ms inline; mid 29.3 vs 2.7). Root cause,
confirmed by A/B on the same host:

- 1.5.4 moved per-doc length into a per-segment sidecar (the ~4.7x size win:
  1421 MB vs 6729 MB inline). To make sidecar lookups fast it decodes the
  **entire segment sidecar once per scan** into a scan-local sorted array
  (`bm25_doclen_cursor_init` -> `bm25_doclens_load`). On a 2.19M-doc single
  segment that is a ~20 MB alloc + ~534 page reads + a FOR-unpack of every
  block — a **fixed ~18 ms per ranked scan regardless of match count.**
- For a rare term (10.8k matches) that fixed decode dwarfs the actual scoring:
  plain `@@@` count is **2.4 ms**, ranked is **~20 ms** — the ~18 ms delta is
  the whole-sidecar decode.
- Inline (`doclen_sidecar=off`) pays length lookup per-posting with locality, so
  rare/mid ranked are 1.6/2.7 ms — competitive with the field.
- Common `year` is 74.7 ms on BOTH (sidecar and inline): that term (735k df,
  34% of the corpus) is posting-scan-bound, not doclen-bound, so the sidecar
  tax is invisible there. (It is also markedly slower than the Aug body-only
  run's 14 ms — the title+body corpus + this host account for some, but the
  common-term posting scan is the next thing to profile.)

The 1.5.0 5-way missed this because it used the OLD page-directory cursor (which
read only the pages covering scored docids), not the 1.5.4 whole-segment decode;
the 1.5.4 validation missed it because it only measured common terms + a small
synthetic corpus where the fixed decode was cheap.

## Verdict

- pg_fts is still the **smallest index** (1421 MB, 25-52% smaller than the
  field) and **uniquely fast + capable** on count/AND/prefix (the ranking-only
  engines can't do these; pg_search's count is 16 ms vs pg_fts 3.8 ms).
- BUT the default sidecar path is **not competitive on ranked latency** because
  of the per-scan full-sidecar decode. The `doclen_sidecar=off` path is fast on
  rare/mid but 4.7x larger and still slow on the common 735k-df term.
- **Neither pg_fts config is competitive on common-term ranked** (74 ms vs
  pg_search 2.3 ms, vchord 4 ms, pg_textsearch 11 ms) — a separate posting-scan
  cost to profile.

## Required next work (this benchmark is the justification)

1. **Persistent build-time sidecar directory (ROADMAP #2/#4).** Replace the
   per-scan whole-segment decode with an on-disk sparse `(docid -> byte-page)`
   directory written at build/merge time, so a ranked scan reads O(log) +
   only the sidecar pages covering its scored docids — no fixed per-scan tax.
   This is the ONLY way to get both the size win (sidecar) AND fast rare/mid
   ranked. The scan-local decode was a stopgap that does not scale to a large
   single segment.
2. **Profile the common-term (735k-df) posting scan** — 74 ms is ~5x the Aug
   body-only number and ~30x pg_search; the block-max WAND is not pruning this
   term well on title+body. Separate from the sidecar issue.

## UPDATE 2026-09-01: page-directory doclen cursor (task #2, partial win)

Instead of an on-disk directory (a format change, high risk given the 1.5.1
inline-metapage-growth outage), the fix is a **relcache-cached page directory**:
a tiny (first_docid, blk) entry per sidecar PAGE, built by walking only page
HEADERS (no block decode), cached in rd_amcache as ONE contiguous chunk keyed
by the metapage generation (satisfies the single-chunk rule the 1.5.4 20MB
decoded array violated). A lookup binary-searches the directory to the covering
page, decodes ONLY that page, keeps it resident. No format change, no REINDEX.

Measured on the same 2.19M host (median, warm), doclen_sidecar=on:

| band       | 1.5.7 whole-segment decode | page-directory cursor | inline (4.7x bigger) |
|------------|----------------------------|-----------------------|----------------------|
| rare  k10  | 25.6 ms                    | ~10 ms  (2.5x)        | 1.6 ms               |
| mid   k10  | 29.3 ms                    | ~11 ms  (2.7x)        | 2.7 ms               |
| common k10 | 74.7 ms                    | ~70 ms                | 74 ms                |

Parity PASS on all bands (k10+k100, single + AND). A 90s concurrent
merge+vacuum+6-reader soak kept the ranked top-10 stable: 0 mismatches, 0
errors, server up (the rd_amcache directory is generation-invalidation-safe).

Honest limits:
- rare/mid improved 2.5x but still above inline (1.6-2.7 ms): a scattered rare
  term still decodes many distinct sidecar pages on demand. Inline pays 0 extra
  reads because doclen travels with the posting. The directory removes the FIXED
  per-scan decode tax, not the per-scattered-page decode -- the irreducible
  sidecar-vs-inline tradeoff.
- common-term (year, 735k df) ranked stays ~70 ms and is NOT a doclen problem:
  EXPLAIN k10 reads 8,115 buffers -- the block-max WAND is not pruning this term
  (plain @@@ count is 2.4 ms). That is the real common-term lever and a separate
  WAND-pruning investigation, independent of the sidecar.
