## Review

**First review** (independent subagent, on b7718f0): six findings, all fixed in 3e2c1f6.

- Medium: a pre-1.17.0 build that met recently-dead rows had their lengths subtracted
  although its total never held them; avgdl 0. Measured 0/0.000 on the first draft,
  2000/10.000 after the fix.
- Medium-low: a cancelled VACUUM could leave totals and N inconsistent.
- Low: 1.5.0-1.5.2 segments' missing inline lengths.
- Low: empty pending documents in N.
- Low: a 1-ulp share overshoot.
- Low: `doclen_sidecar` switched off on a live index, now a documented known issue
  (measured +1.3% after deleting a third).

**Second review** (fresh subagent, on 3e2c1f6): three accuracy findings, fixed in
a80630a.

- The live count is now exact (it subtracts only the tombstones the walk met).
- A floor keeps the length total at least N.
- A sidecar merge output does not count unknown lengths.

Neither review built or ran anything.  Their scenarios that could be built were run here
(the 1.16.0-build cases below are in the upgrade gate).

## A/B: 1.16.0 vs 1.17.0 (c6id.metal, PG 18.6)

`data_170_2026-11-09/ab170.sh`, `ab170.log`.  1.9M rows (40-160 tokens), one packed
segment, 1/80 of the rows deleted (23,750 scattered tombstones), `doclen_sidecar = off`
for the query state.  The host was tuned with turbo off, the performance governor and
THP never, and the server was pinned to node 0.

**Correctness first.**  The top-10/top-200 ids of `patch`, `vacuum` and `remove` are
identical on 1.16.0, 1.17.0 and a REINDEX of the same rows.  At 1/80 deleted the avgdl
error is only 1.3% (103.367 vs 102.075), too little to move these top-k.  After each
VACUUM 1.17.0's stats equalled the table in all six runs (N 1,876,250, avgdl 102.075);
1.16.0 read 103.367.

**VACUUM wall time** after the same delete, on a fresh index per run, 3 reps per arm, run
order alternated:

| `doclen_sidecar` | 1.16.0 median | 1.17.0 median | diff |
|---|---:|---:|---:|
| off (inline: a second posting walk for the dead lengths) | 18.356 s | 19.067 s | +3.9% |
| on (sidecar read) | 0.791 s | 0.817 s | +3.2% |

There is no A/A arm for VACUUM.  The 1.16.0 spread was 18.31-19.22 s, so the off row is
within one rep of overlapping.

**Ranked latency** on the post-VACUUM state, the `.so` swapped on one index.  Each value
is the median of 11 per sample, over 12 samples per build (6 ABBA rounds), with an A/A
pair:

| query | 1.16.0 ms | 1.17.0 ms | diff | A/A |
|---|---:|---:|---:|---:|
| `patch`, top-10 | 1.878 | 1.889 | +0.61% | +0.32% |
| `vacuum`, top-200 | 4.684 | 4.729 | +0.94% | +0.05% |
| `remove`, top-200 | 20.695 | 20.846 | +0.73% | +0.08% |

The ranked scan's own code changed by one branch, the avgdl guard.  The arms differ by
the whole release, including sparsemap 5.8.5, whose vetting measured +1.2% / +0.5% / 0%
on the same three queries (`RESULTS_SM585_2026-11-05.md`).  The cause of the 0.6-0.9% is
not isolated.

The run was c6id.metal on PG 18.6, with the script as sent (`gate170/churn_repro.sql`):
1,880,000 rows, 23,313 moves, `doclen_sidecar = off`.  `churnrun.sh` patches only the
probe, which also prints N and avgdl against the table, and wraps each VACUUM and
`fts_vacuum` in `\timing`.  Logs are `churn-{old,new}.log`.

- **Rows B and C (N above the table).** The moved rows' old versions are deleted but
  not yet vacuumed, so the index still counts them; both releases agree.
- **avgdl.** It equals the table from row D on in 1.17.0.  1.16.0 drifts with each
  round (103.355, 103.356, 104.619) and only REINDEX resets it.  The 1.88M-row
  production copy in the 2026-11-04 report read +3.6% after three rounds; this run reads
  +2.5% at its third.
- **Ranked timings** are equal between releases.
- **Maintenance timings** (`\timing`, one run each, no A/A), 1.16.0 vs 1.17.0:

  | statement | 1.16.0 | 1.17.0 |
  |---|---:|---:|
  | first `fts_vacuum` (2 segments, dead heap rows, nothing tombstoned) | 101.4 s | 100.4 s |
  | `VACUUM` after moves (three times) | 20.9 / 20.8 / 20.9 s | 22.5 / 22.8 / 22.8 s |
  | `fts_vacuum` expunge of 23,313 tombstones (twice) | 67.6 / 69.6 s | 67.2 / 68.0 s |

  VACUUM is +8-10% here (+1.6 to +2.0 s, three of three); the A/B measured +3.9%.  The
  extra work is the second posting walk with `doclen_sidecar = off`, which finds the dead
  documents' lengths.  Why its share differs from the A/B is not isolated: the
  vocabulary and the delete pattern differ.  The `fts_vacuum` expunge is unchanged.
