# 5-way BM25 comparison — pg_fts 1.5.8 vs the field (2026-09-04)

Re-run of the 5-way with **pg_fts 1.5.8** (the page-directory doclen cursor), all
four engines rebuilt from scratch on identical fresh hosts and an identical
corpus.

## Rig
- EC2 r6id.4xlarge (account `bene`), Intel Xeon 8375C @ 2.90GHz, 16 vCPU, 128GB,
  884GB local NVMe instance store, Amazon Linux 2023, PostgreSQL 17.10 built from
  source, `shared_buffers=64GB`, prewarmed. One dedicated instance per engine.
- Corpus: wikimedia/wikipedia 20231101.en, first **2,188,038** articles
  (heap 3914 MB). df bands: rare=slovakia, mid=hungary, common=year.
  **CAVEAT -- the indexed COLUMNS were not uniform across engines; see
  "Indexed-column mismatch" below. This run is NOT fully apples-to-apples on the
  common-term band.**
- Warm `\timing`, **median of 5 runs with the first (cold) dropped**, on every
  engine.
- Versions: pg_fts 1.5.8; pg_textsearch `f940210`; pg_search (Tantivy)
  paradedb `f4b1f65` / pgrx 0.19.2 / pgvector 0.8.5; VectorChord-bm25 `14fc2a3`
  / pgrx 0.17.0.

## Correctness

pg_fts ranked top-k **parity PASS** on every band (k=10 and k=100, single-term
and AND) against an exact `fts_bm25` sort — zero genuine misses. The other
engines were verified only for expected row counts.

## Reading the numbers

**Where pg_fts wins:**
- **Smallest index by 25-52%** (1421 MB vs 1885/2723/2905).
- **count(*) 2.35 ms vs pg_search 13.75 ms (5.9x faster)** — and the two
  ranking-only engines cannot answer it from the index at all.
- **AND 0.88 ms vs pg_search 3.30 ms (3.7x faster)**.
- **prefix competitive** (2.28 vs 2.05 ms).
- Exact top-k, verified by the parity harness.

**Where pg_fts loses:**
- **Ranked latency across every df band.** rare 10.2 / mid 11.3 / common 60.9 ms
  vs pg_search 2.06-2.22 ms. The cause is measured and documented in
  `bench/NOTE_WAND_PRUNING_2026-09-04.md`: the block-max WAND prunes essentially
  nothing on this corpus (0 block-skips on rare/mid; the scan scores ~every
  posting), because the impact distribution is a flat plateau — the bound is
  already exactly tight and finer blocks would not help. Fixing this needs
  impact-ordered postings or opt-in early termination, not a bound tweak.
- **phrase**: 128 ms with `positions=on` (which costs 13 GB, ~9x the default
  index) vs pg_search 22 ms. With the default `positions=off` a phrase degrades
  to a full heap recheck (~8.3 s) — that is a documented config tradeoff, not a
  bug, but it means phrase-heavy workloads must opt into positions.

## Changes vs the 1.5.7 run (bench/RESULTS_5WAY_157_2026-09-01.md)

pg_fts rare/mid ranked improved from 25.6/29.3 ms to **10.2/11.3 ms** — the
1.5.8 page-directory doclen cursor delivering the promised ~2.5x. Common-term
ranked is unchanged (~61 vs ~70 ms), as expected since that band is

Absolute competitor numbers moved from the previous run because the corpus

pg_textsearch is very sensitive to document length (rare 0.86 -> 7.4 ms, common
11.0 -> 20.8 ms); pg_search and vchord barely moved.

## Indexed-column mismatch (a real flaw in this run)

The table loaded on every host was `docs(id, title, body)`, but the engines did
NOT all index the same columns:

| engine        | indexed text          |
|---------------|-----------------------|
| pg_fts        | **title + body**      |
| vchord        | **title + body**      |
| pg_search     | **body only**         |
| pg_textsearch | **body only**         |

This is my error in the per-engine instructions, not an engine difference. The
consequence is visible in the per-term match counts on the SAME corpus:

| term     | pg_search matched | pg_fts df | delta |
|----------|-------------------|-----------|-------|
| slovakia | 10,852            | 10,875    | +0.2% (analyzer noise) |
| hungary  | 23,987            | 24,097    | +0.5% (analyzer noise) |
| **year** | **495,569**       | **734,896** | **pg_fts matched 48% MORE docs** |

So on rare/mid the engines are effectively comparable (the tiny deltas are
tokenizer/stemmer differences), but on the **common band pg_fts and vchord
scanned ~48% more postings than pg_search and pg_textsearch** because `year`
appears in many titles. The common-term column therefore OVERSTATES the gap
against pg_fts/vchord to some degree.

It does NOT explain the gap away: even normalizing for 48% more postings, pg_fts
would be ~41 ms vs pg_search's 2.2 ms, and the independently-measured root cause
(`bench/NOTE_WAND_PRUNING_2026-09-04.md`: 0 block-skips, ~every posting scored)
is a property of pg_fts's traversal, not of corpus size. The rare/mid bands --
where the corpora ARE comparable -- still show 10.2/11.3 ms vs 2.06-2.38 ms.

**To fix in the next run:** index exactly the same text everywhere. Either drop
`title` from the pg_fts/vchord expressions, or add a generated
`content = title || ' ' || body` column and point all four engines at it.

## Methodology footnotes (per-engine query forms + caveats)

Exact ranked forms used, for reproducibility:

- **pg_fts**: `SELECT count(*) FROM fts_search('docs_fts', to_ftsquery('english','<term>'), k)`
  (and `d @@@ to_ftsquery(...)` / `ORDER BY d <=> to_ftsquery(...)` for the
  boolean/KNN variants). Index: `CREATE INDEX ... USING fts (d)` (defaults:
  `positions=off`, `doclen_sidecar=on`).
- **pg_textsearch**: `SELECT id, body <@> '<term>'::bm25query AS score FROM docs
  ORDER BY score LIMIT k`; index `USING bm25(body) WITH (text_config='english')`;
  requires `shared_preload_libraries='pg_textsearch'`.
- **pg_search**: `SELECT id FROM docs WHERE body @@@ '<term>' ORDER BY
  paradedb.score(id) DESC LIMIT k`; phrase via the `###` operator; prefix via
  `pdb.parse('body:hung*')`; index `USING bm25(id, body) WITH (key_field='id')`;
  requires `shared_preload_libraries='pg_search'` + pgvector + openblas-devel.
- **vchord**: `SET "bm25.limit" = k;` then `... ORDER BY tv <&>
  to_bm25query(to_tsvector('english','<term>'), 'docs_vc') LIMIT k`. NOTE the
  installed signature is `to_bm25query(tsvector, regclass)` -- the query term is
  a **tsvector first**, index regclass second (the reverse of what a naive
  `to_bm25query('docs_vc','<term>')` guess produces; that form does not exist).
  Needs a materialized `tsvector` column (its `bm25_ops` is FOR TYPE tsvector)
  and `shared_preload_libraries='vchord_bm25'`.

Caveats:
- **pg_textsearch indexed 2,188,031 of the 2,188,038 loaded rows** (7 fewer;
  reported by its own build notice, `avg_length=313.91`). Not NULL/empty-string
  related and not chased further — far below any level that affects the latency
  medians, but recorded for completeness.
- pg_fts is the only engine whose ranked output was verified **exact** here (the
  parity harness vs an `fts_bm25` sort). The others were checked only for
  expected row counts, so a hypothetical recall shortfall in a competitor would
  not show up in these latency numbers.
