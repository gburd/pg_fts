# Plan: I10, I11, I12 (2026-10-15)

Written before the code and before any measurement.  Everything runs on Debian 13 EC2
hosts in the kiwi account; nothing is built or run on the workstation.

## I12: ranked reads under sustained inserts

**Observation** (`RESULTS_PGTS_METAL_2026-10-15.md`, write band).  8 inserters and 8
rare-k10 readers ran for 120 s with `fts_merge` every 30 s:

| | inserts/s | ranked reads/s |
|---|---|---|
| pg_fts | 39-56k | 56-221 |
| pg_textsearch | 9-21k | 819-1,602 |

**Mechanism, to be confirmed by measurement first** (rule 12):
- Only VACUUM, `fts_merge` and autovacuum flush the pending list into a segment; an
  insert never does.
- Since 1.13.0 every ranked query reads the whole pending list, decompressing and
  matching each pending document.
- At 55k inserts/s the list grows by 1.6M documents between 30 s merges, so each read
  costs O(pending).

**Step 1: measure.**  Ranked rare-k10 latency and one backend's work as functions of
pending length (0, 10k, 100k, 1M), on a 2.19M-row index.  Also measured:
- the cost of one `fts_merge` / flush at each length;
- the insert rate of 8 clients with no readers.

The second is the advantage that must be kept: an insert appends to a pending page
under the metapage lock, and that is cheap.

**Step 2: candidate fixes, chosen by the measurement.**
- **(a) Bound the pending list: auto-flush.**  When `npending` (or pending bytes)
  passes a threshold, flush it to a segment.  The cost must not land on the inserting
  backend's latency, so either:
  - a conditional maintenance lock, where the inserter that crosses the threshold
    flushes and the others skip (like the existing conditional merge); or
  - a background worker woken by the inserter (more code).

  Start with the conditional inline flush.  If the insert rate drops beyond the A/B
  spread, move to a worker.  A GUC `pg_fts.pending_flush_threshold` (rows), default
  chosen by the measurement and 0 to disable, so existing behaviour is one setting
  away.
- **(b) Make reading pending cheaper.**  For a ranked query, decide each pending
  document by term presence before decompressing or scoring.  The pending item's
  ftsdoc term array is sorted, so `fts_doc_lookup` is a binary search, which is
  already the case.  The likely cost is the walk itself: buffer pins on thousands of
  pending pages, plus validation.  So (b) helps by a constant factor at most; (a) is
  the structural fix.
- (c) Do not skip pending in ranked results.  Correctness since 1.13.0 is that ranked
  scans include pending documents; that is not traded away.

**Correctness gates:**
- `pending_rank` keeps passing (scores before a flush equal those after).
- `t/012` concurrency, 3 runs.
- In the write band, the index count equals the heap count.
- A new test asserts that the pending list stays bounded under inserts with the
  threshold set (it fails with threshold 0).

**Success criterion** (pre-registered).  The metal write band is re-run with the same
harness on c7gd.metal and c6id.metal (one each is enough for an A/B against
1.13.0 on the same host):
- ranked reads/s >= pg_textsearch's on the same host;
- insert rate >= 2x pg_textsearch's (it is 2.6-6.3x today);
- both reproduced on a second pass.

## I11: expression-index ranked LIMIT >= 250 takes bitmap + Sort

**Observation** (smoke test, 50k rows).  For `ORDER BY to_ftsdoc(...) <=> q LIMIT 1000`
the planner chose a Bitmap Heap Scan plus Sort, which took 21.6 s against 4-7 ms on the
ordering scan.  Two causes:
- `@@@` uses `tsmatchsel`, which returns the default selectivity 0.005 for non-tsvector
  operands, so every query is estimated at 250 rows per 50k;
- `to_ftsdoc` and `fts_distance` are declared COST 1, so re-evaluating them per match
  in the Sort looks free.

**Candidate fixes** (each verified on EXPLAIN and timing):
1. **Realistic COST.**  `to_ftsdoc(regconfig, text)` COST 100, the same as
   `to_tsvector`.  This needs a SQL upgrade script (`ALTER FUNCTION ... COST`), so it
   goes in a minor release.
2. **A restriction estimator for `@@@`** (`fts_matchsel`).  For a Const ftsquery it
   estimates selectivity from the index's dictionary df.  `fts_count`'s dict-df fast
   path already reads it; with several terms it combines them by the boolean structure
   (bm25_query_maxhits already computes this bound).  This also fixes the row estimates
   for bitmap scans and joins.
3. Verify the ordering-scan cost (`bm25_costestimate`) stays sublinear in LIMIT.

**Gates:**
- An EXPLAIN test (`sql/planner_cost.sql`, new): on a table where the ordering scan is
  right, the ranked `LIMIT 1000` plan is an Index Scan with no Sort.  It fails on
  1.13.0 if reproducible at test scale; otherwise its EXPLAIN rows estimate is checked.
- Timing at 50k and 2.19M rows, before and after.
- Rule 15: check every operator that uses `tsmatchsel` (both `@@@` commutators).

## I10: sanitizers CI job never runs the tests

**Observation.**  Under pg_virtualenv, the ASan-built `.so` fails at `CREATE
EXTENSION`, so every regression test fails and the job, marked `continue-on-error`,
reports success.

**Fix.**  Build PostgreSQL itself with `-fsanitize=address` in the job (about 4 min on a
GH runner, cacheable), install pg_fts into it, and run `make installcheck` against a
server started from that build.  Then drop `continue-on-error` from the regression step.
This was proven first on a Debian EC2 host with the same commands, then in CI.
`doc/testing.md` describes what the job covers.

**Gate.**  The job runs all 16 regression tests with `ok` on GitHub.  A planted
use-after-free in a throwaway branch makes it fail; it is checked once and not
committed.
