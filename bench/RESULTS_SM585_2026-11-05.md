# sparsemap 5.8.5 vendored: the cursor fix for ROADMAP I29 (2026-11-05)

**Current.**  The sparsemap maintainers' reply to pg_fts's report is in
`data_sm585_2026-11-05/sparsemap-5.8.5-reply.md`; the report itself is
`data_cbmc_2026-11-03/sparsemap_issue/`.  Their fix is 5.8.5 (tag `v5.8.5` 6be665c, on
Codeberg and GitHub).  pg_fts vendors it unchanged apart from the `__pg_bm25_` prefix
block: `vendor/sm.c` is v5.8.5 plus 9 lines, and `vendor/sm.h` is v5.8.5 byte for byte.

## What the reply claims, checked here

| claim | check | result |
|---|---|---|
| no ABI change | `sizeof(sm_cursor_t)`, `SM_CURSOR_INIT` (`abi.c`); the `sm.h` diff | 24 bytes and `{SIZE_MAX, 0, SIZE_MAX}` on both; `sm.h` changes only the version and comments |
| the walk never starts at `prev_offset` | read `e6bb583` | the gap-resume branch is removed; a gap lookup caches the neighbour the walk stepped over (`prev_off`, with `prev2_off` as its hint); `__sm_map_set` takes the hint only when the cursor sits on the returned chunk |
| the reproducer passes | `repro_wrong_answer.c` against v5.8.5 | 0 DIFFER, exit 0 (5.8.4: DIFFER at hint 16, exit 1) |
| reachability harnesses: 0 wrong | `stale_hint_api`, `stale_hint_search`, `stale_hint_mutation`, `grow_cursor_check` | 0 wrong on all four (0 invalid maps in `stale_hint_mutation`) |
| `sm_next_member` checked no start word | `nextmember_check2.c`: every 8-byte offset x every real chunk start, 20,000 maps | 5.8.4: 1,614,722 wrong of 2,307,793; 5.8.5: 1,170 wrong, **all** at offsets whose word equals the recorded start, none at a real chunk start |
| the speedup is kept | `gapcost.c`: 100,000 ascending gap lookups over 20,000 chunks, best of 5 | 5.8.3 2,642 ms; 5.8.4 3.43 ms; 5.8.5 3.44 ms |
| the CBMC harness verifies | `test/cbmc/smcursor_harness.c`, CBMC 6.6.0, the 4 layouts | C1, C2, C3 and C3x (any `prev_offset`) verify on all four; the new C4 (stale offset with a real start_idx, from their reply) verifies on all four; C4 FAILS on `mutate_sm.py`'s copy without the start-word check |

The 1,170 remaining `sm_next_member` mismatches are the case the reply and the new
`sm.h` call out: a stale cursor whose offset lands on a payload word that happens to
equal the recorded start index. Closing that would need cursor state that 5.8.x lacks
(an ABI change). pg_fts never holds a cursor across a mutation, so this case cannot
reach it.

## Cost in pg_fts (`smab.sh`, `smab.log`)

Setup:

- **Host and server:** c6id.4xlarge, PG 18.6. A c6id.metal was unavailable in all three
  us-east-2 zones (InsufficientInstanceCapacity).
- **Index state:** the churn S3 state, 1.9M rows with about 23.7k scattered tombstones on
  one packed segment. This state puts the tombstone cursor on every ranked posting.
- **Builds:** one index, with the `.so` swapped between v1.16.0 (sparsemap 5.8.4), the
  same tree built twice (A/A), and v1.16.0 + sparsemap 5.8.5.
- **Sampling:** each sample is one psql session, taking the median of 11 runs; 12
  interleaved samples per build.

**Correctness:** the md5 of every query's ranked ids is identical across builds.

| ranked query | 5.8.4 ms | 5.8.5 ms | diff | A/A |
|---|---|---|---|---|
| `patch`, top-10 | 1.719 | 1.739 | +1.16% | +0.06% |
| `vacuum`, top-200 | 10.578 | 10.634 | +0.54% | +0.14% |
| `remove`, top-200 | 51.736 | 51.725 | -0.02% | +0.11% |
| `patch`, top-10, first query of a session | 5.849 | 5.835 | -0.23% | -0.68% |

**The top-10 is a small, consistent cost.** 5.8.5 is slower in all 6 rounds (by +0.11%
to +1.80% per round), while the A/A pair moves between -1.08% and +0.64%.

**The cause is not the lookups themselves.** Standalone, 5.8.5 is no slower
(`stepcount.c`):
- ascending gap lookups take 28.9 ns, against 31.2 ns on 5.8.4;
- member lookups take 54.4 vs 54.5 ns.

A pass over this tombstone shape (`scattered_ab.c`) is 164.3 vs 162.8 ms, which is
+0.9%.

**Verdict:** NOISY at the 1% level, with a real but unexplained +1.2% on one query. The
correctness fix stands, and the cost is far below the 60-300x this cursor path was
introduced to remove (ROADMAP I25).
