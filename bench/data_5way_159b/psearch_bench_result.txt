MEASUREMENTS
------------
Methodology: psql -f <file>.sql with \timing on, 6 runs per query, first (cold) run dropped,
median of the remaining 5 reported. Times are the value from psql's "Time:" line (planning +
execution, single-statement file).

All exact query forms used:

  rare k10:      SELECT id FROM docs WHERE content @@@ 'slovakia' ORDER BY paradedb.score(id) DESC LIMIT 10;
  mid k10:       SELECT id FROM docs WHERE content @@@ 'hungary' ORDER BY paradedb.score(id) DESC LIMIT 10;
  common k10:    SELECT id FROM docs WHERE content @@@ 'year' ORDER BY paradedb.score(id) DESC LIMIT 10;
  common k100:   SELECT id FROM docs WHERE content @@@ 'year' ORDER BY paradedb.score(id) DESC LIMIT 100;
  count(year):   SELECT count(*) FROM docs WHERE content @@@ 'year';
  AND:           SELECT id FROM docs WHERE content @@@ 'slovakia AND hungary' ORDER BY paradedb.score(id) DESC LIMIT 10;
  phrase:        SELECT id FROM docs WHERE content ### 'united states' ORDER BY paradedb.score(id) DESC LIMIT 10;
  prefix:        SELECT id FROM docs WHERE content @@@ pdb.parse('content:hung*') ORDER BY paradedb.score(id) DESC LIMIT 10;

Row counts confirmed before timing (all correct: k10 -> 10 rows, k100 -> 100 rows).

Results (median of 5, first of 6 runs dropped; all 5 raw timings in ms shown):

MATCH COUNTS (SELECT count(*) FROM docs WHERE content @@@ '<term>')
---------------------------------------------------------------------
  slovakia : 10853
  hungary  : 23990
  year     : 495580

Note: Tantivy (pg_search's engine) does not stem by default. The 495580 match count for
"year" reflects only literal-token matches of "year" (not "years", "yearly", etc.), which is
why it is far lower than a stemming PostgreSQL tsvector-based engine would report for the same
term on identical text. This confirms the prior-run observation on this identical corpus.
