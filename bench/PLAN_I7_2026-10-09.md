# Plan: I7, fewer shared-buffer reads per ranked query (2026-10-09)

Written before the code.  ROADMAP I7; cause in `bench/RESULTS_TPS_VARIANCE_2026-10-09.md`.

## What a rare top-10 reads today (measured, release 1.11.0, 2.19M docs, one segment)

`slovakia` k10: 278 shared buffers (`EXPLAIN (ANALYZE, BUFFERS)`); `fts_index_df` alone,
which is one dictionary lookup per segment: 85 (`aardvark` 32 ... `zzzz` 103, by where the
term sorts in the 85-page dictionary-index chain).  A ranked scan does that lookup three
times per (term, segment):

1. `bm25_query_maxhits` (gettuple, once per scan): global df bound;
2. `bm25_topk_candidates_range` pass 1: global df for IDF;
3. `bm25_topk_candidates_range` pass 2: the cursor (df, max_tf, first posting).

and `bm25_dict_seek` re-walks the dictionary-index chain from its head each time: a
linear chain of ~85 pages, binary-searched per page, so a lookup reads every index page up
to the target.  Every page read is a buffer pin and a share content lock: shared cache
lines every concurrent query writes.

## Change

A. **Dictionary-index directory in the relcache.**  On first use per backend and
   metapage generation, read each segment's dictionary-index chain once into a packed
   in-memory array of (first term, dict block), and binary-search that instead of the
   chain.  Lives in the existing `rd_amcache` chunk (`BM25DoclenDirCache`, one palloc,
   rebuilt when `generation` changes), so no new cache, no new lifecycle.  Size: one
   entry per dictionary page, ~29k for this index, ~0.6-1.2 MB per backend.  A seek then
   reads ONE buffer (the dictionary page) instead of 1-85 index pages + 1.
   Validity: a segment's dict/dict-index pages are immutable while the segment is in the
   directory; every directory change (add, merge, flush, vacuum rewrite) bumps
   `generation` (5 sites, all checked); the scan already re-checks `generation` at the end
   and restarts if it moved, and a segment's pages are not recycled while a snapshot that
   could see it is alive (recycle gate).  So a directory built at generation G is exactly
   as valid as the metapage snapshot of a scan at G.  Key the cached segment entries by
   `dictindexstart` (and `dictstart`), and fall back to the chain walk for any segment
   not found in the cache.  Scope: the ranked path only (`bm25_query_maxhits`,
   `bm25_topk_candidates_range`); the collect, count, prefix, fuzzy and `fts_index_df`
   paths keep the chain walk (unchanged, and none of them repeats a lookup).  A segment
   whose index chain looks malformed (empty or oversized entry) is not cached, so it
   takes the chain walk, which stops at the same place.  Size counts against
   `pg_fts.doclen_cache_mb`, the existing per-backend budget for this chunk.
B. (DROPPED before coding: with A a lookup reads one dictionary page, so the three lookups
   cost ~3 buffers; deduplicating them saves ~2.  Measured basis: `fts_index_df`, one
   lookup, costs 85 buffers for `slovakia` of the scan's 278.)
   **One lookup per (term, segment) per scan.**  Pass 1 and pass 2 of
   `bm25_topk_candidates_range` keep pass 1's result for pass 2.  `bm25_query_maxhits`
   is left alone (once per scan, and with A it costs one buffer per segment per term).

No speedup is predicted here; the gate below reports buffers per query and tps for both
builds.

## A/B (decides whether it ships)

- Correctness first: release vs I7 build, identical ids and index scores on every band of
  the 1.11.0 protocol, plus the exhaustive OR/AND/phrase references; regression suite and
  TAP green (nix pg17/pg18).  A test that the directory is rebuilt after a merge (a term
  added by a new segment is found; a merged-away segment is not consulted).
- Buffers per query (`EXPLAIN BUFFERS`) on the bands, both builds.
- Throughput: rare, mid, common k10 and `count(*)` at 16 and 64 clients, alternating
  release / I7, 3 rounds, on at least one host in the fast state and one in the slow state
  (state identified by `mbench2.c` before and after); single-client latency as the
  protocol.
- Ships if: results identical; never slower than the release beyond the same-arm spread
  on any band, host or client count; faster on at least the slow host.  Otherwise it is
  recorded as rejected with its numbers.
