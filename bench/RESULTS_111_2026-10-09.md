# 1.11.0 release benchmark (aarch64 Debian, 2026-10-09)

Protocol: `bench/PROTOCOL_111_2026-10-09.md`, committed (da4cf62) before any host was
launched.  Raw data: `bench/data_111_2026-10-09/` (one directory per engine, harness in
`harness/`, tables recomputed by `harness/summarize.py`).

pg_fts **1.11.0** as released: built on the host from the PGXN zip (sha256 `fff822fe...`
checked before the build), binary md5 `da915fc2`.  The second pg_fts arm is **39b6a42**
(md5 `4486203a`, byte-identical to the binary `RESULTS_A_2026-10-07.md` measured), on the
same host and the same index files.  Competitors at their latest release on 2026-10-09:
pg_textsearch **1.5.1**, pg_search **0.26.1** (released 2026-10-08; RESULTS_A had 0.26.0),
VectorChord-bm25 **0.3.0** with pg_tokenizer **0.1.1**.

Rig as RESULTS_A: one EC2 r7gd.4xlarge per engine (Graviton3 Neoverse-V1, 16 vCPU, 128 GiB,
local NVMe), Debian 13 arm64, PostgreSQL 17.10 from source with identical flags and
settings.  Corpus: 2,188,038 Wikipedia articles, md5 `f5939e85...` on all four hosts.  All
four hosts ran concurrently, 01:29-03:47 UTC, and were terminated afterwards.

## Correctness gate (before any timing)

- pg_fts: the release and 39b6a42 return identical ids and index scores (within 1e-9) on
  all 12 bands and the count (`fts/gate_*`).
- The release arm against the exhaustive references computed from the stored documents
  with the index's statistics and length quantization: OR (`film | music | album | band`,
  `slovakia | hungary`, k = 1/10/100) 6 cases, 0 differ; AND (`united & states`,
  `slovakia & hungary`, `world & war`) 9 cases, 0 differ; phrase (`"united states"`,
  `"world war"`, positions index) 6 cases, 0 differ (`fts/oracle_*.txt`).
- Every band returns k rows on every engine that can express it.
- Match counts against the regex ground truth are unchanged from RESULTS_A: pg_fts and
  pg_textsearch 10,875 / 24,097 / 734,896, pg_search 10,898 / 24,152 / 735,955, regex
  10,898 / 24,148 / 733,960.

## Release vs 39b6a42 (same host, same index files)

Latency: the two arms' pass spreads overlap on 10 of 12 bands.  The two that do not point
in opposite directions: mid k10 is 3.4% slower on the release (0.42 [0.41-0.43] vs 0.41
[0.40-0.41] ms) and `"united states"` 5.0% faster (2.84 [2.80-2.90] vs 2.99 [2.98-3.06]).
The release's code differs from 39b6a42 only on the write, flush, free and truncate
paths; neither band's query path changed, so these are reported as measured and not
attributed (layout effects of this size were seen before: CHANGELOG 1.9.1).  Settled
throughput: overlapping on every band and client count but one (`count(*)` at 16 clients,
74,309-74,715 vs 74,818-75,022, 0.4%).  Cold: within 2.1 ms on every band and both
`effective_io_concurrency` settings, identical buffer reads.  Builds: within 4.1 s.
**The release did not change query performance beyond +-5%, in both directions** -- the
question the protocol was written to answer.

pg_textsearch's boolean and phrase forms (`content @@ to_tsquery(...)` ordered by its BM25
operator) are sequential scans; every execution hit the 300 s statement timeout.  This run's
`extra_bands.sh` skips a band's later passes after a timeout (RESULTS_A did the same by hand
after one pass; `harness/extra_bands_skipto.sh`).  Phrase bands use pg_fts's
`positions = on` index; all other pg_fts bands use the default index.

Against the field, pg_fts 1.11.0 has the lowest latency on 10 of 12 bands: 1.7-14.8x
pg_textsearch on single terms (the only bands where pg_textsearch uses its index, apart
from the 4-term OR, 1.05x), 2.1-5.4x pg_search on single terms, small booleans,
`united & states` and `"united states"`, 1.8x on `"world war"`, 48x on the exact count.
pg_search is lower on `world & war` (5.75 vs 5.87, 2%) and on the 4-term OR (13.40 vs
13.97, 4%); on `world & war` the spreads overlap (pg_fts 5.70-5.87, pg_search 5.75-5.76),
on the 4-term OR they do not.  These are the ROADMAP A2 bands, unchanged by this release.

engine, band and client count.  VectorChord's second settled run stopped after its rare band when the host was

pg_fts throughput relative to RESULTS_A (same binary for the 39b6a42 arm, a different host
of the same type): rare c16 23,765 here vs 26,750, mid 34,050 vs 35,304, common 18,859 vs

others, and one host can switch between the two; this run landed in the slow state, the
RESULTS_A run in the fast one.  The scoreboard ratios against the other engines are taken
within this run.

## Drift against RESULTS_A (same versions)

- pg_textsearch 1.5.1: within 1% on every single-term band (rare 0.99 vs 0.99, common
  10.69 vs 10.71), 4-term OR 14.63 vs 14.98 (-2.3%); build 266.7 vs 268.3 s; same size,
  same counts.
- VectorChord-bm25 0.3.0: **faster on every band than in RESULTS_A** (rare 13.56 vs 20.38,
  mid 26.56 vs 36.84, common 72.36 vs 84.47, OR 7.90 vs 12.57, 4-term OR 42.36 vs 50.94;
  rare tps at 16 clients 366 vs 334), same plans (`explain.txt` identical), same index size,
  same .deb versions.  Model and tokenize steps were also faster (839 vs 910 s, 2,407 vs
  3,049 s).  Unmeasured cause; the index (42 GiB) does not fit in `shared_buffers`
  (32 GB), so its latency depends on what the page cache holds after the long tokenize
  phase.  Reported as drift, not as a VectorChord change.
- pg_search 0.26.0 -> 0.26.1 (a version change): within 6% on every ranked band (rare 2.59
  vs 2.66, common 2.63 vs 2.63, `united & states` 11.61 vs 11.97, 4-term OR 13.40 vs 13.92,
  phrase 11.41 vs 12.08, -5.5%); exact count 18% faster, 8.64 vs 10.56 ms, and count tps
  at 16 clients 945 vs 773 (0.26.1's notes list "count query matches directly on fully
  visible segments").

## What this does not show

As RESULTS_A.  In addition:

- **Concurrent-write band** (release only, protocol change 6): 8 single-row inserters at
  45,198 tps and 4 rare k10 readers at 5,506 tps for 120 s, with `fts_merge` every 30 s, on a
  109k-row table; 0 failed transactions; afterwards index count == heap count (5,423,568 ==
  5,423,568); 0 maintenance errors; 0 ERROR or signal terminations in the server log.  It is
  a correctness check under the load the release fixed, not a comparison; no other engine
  ran it and 39b6a42 was deliberately not timed on it (it can lose rows under this load).
- Relevance quality, x86, network storage: not measured.
