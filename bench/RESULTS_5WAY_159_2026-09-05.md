# 5-way BM25 comparison — identical single-column corpus (2026-09-05)

The run that removes the asterisk. Every engine indexes **byte-identical text**:
the corpus TSV was pre-joined to exactly two columns (`id`, `content` where
content = Wikipedia title + ' ' + body), each engine loaded
`docs(id bigint, content text)`, and each built its index on `content` and
nothing else. 2,188,038 rows on every host, verified.

pg_fts here is **1.5.8 plus a block-granular doclen decode** (see "The rare/mid
improvement" below).

## Rig
EC2 r6id.4xlarge (account `bene`), Xeon 8375C @ 2.90GHz, 16 vCPU, 128GB, 884GB
local NVMe instance store, Amazon Linux 2023, PostgreSQL 17.10 built from source,
`shared_buffers=64GB`, prewarmed. One dedicated instance per engine. Warm
`\timing`, median of 5 with the first (cold) run dropped.

Versions: pg_fts 1.5.8+; pg_textsearch `f940210`; pg_search paradedb `f4b1f65` /
pgrx 0.19.2 / pgvector 0.8.5 / pg_search 0.25.6; VectorChord-bm25 `14fc2a3` /
pgrx 0.17.0.

## THE HEADLINE: the engines are not answering the same query

With provably identical input text, the per-term **match counts still differ**:

| term     | pg_fts  | vchord (tsvector) | pg_search | pg_textsearch |
|----------|---------|-------------------|-----------|---------------|
| slovakia | 10,875  | 10,875            | 10,853    | (see raw)     |
| hungary  | 24,097  | 24,097            | 23,990    | (see raw)     |
| **year** | **734,896** | **734,896**   | **495,580** | (see raw)   |

pg_fts and vchord agree **exactly** (both use PostgreSQL's `english` text-search
config). pg_search is within 0.2-0.4% on rare/mid but **33% lower on `year`**.

Ground truth on this corpus (regex word-boundary counts, run on the same table):

| pattern        | docs    |
|----------------|---------|
| `\myear\M`     | 501,231 |
| `\myears\M`    | 461,682 |
| `\myears?\M`   | **733,960** |

and `to_ftsdoc('english','year years yearly')` -> `'year':3`, exactly as
`to_tsvector('english', ...)` does.

**So: pg_fts/vchord return the STEMMED result set (year + years + yearly =
~734k docs, matching the 733,960 ground truth), while pg_search returns
~495,580 ~= the literal `year` count (501,231) — i.e. Tantivy is not stemming
under this configuration.** On the common band pg_fts is scoring ~48% more
postings AND returning the linguistically-correct English result set.

This is a semantic difference, not a corpus or methodology artifact, and it must
be stated whenever the common-term column is quoted.

## The rare/mid improvement shipped with this run

Analysis of where rare/mid ranked time goes, and what it cost:

A single-term top-k **provably must examine every posting's (tf, dl)** — impact
is a function of both, neither is ordered in a docid-ordered posting list, so no
bound can exclude a run (this is also why the block-max WAND cannot prune here;
see `NOTE_WAND_PRUNING_2026-09-04.md`). Therefore the only lever for rare/mid is
**making per-posting scoring cheaper**, not scoring fewer postings.

Measured cost breakdown before the fix: rare `slovakia` ranked 10.2 ms vs a plain
`@@@` count of 2.35 ms -> ~7.9 ms was pure ranking overhead on only 10,875
postings (~730 ns/posting). The culprit: 1.5.8's page-directory cursor decoded
the **whole sidecar page** (~31 blocks, ~4,000 doc entries) per lookup, and a
rare term scattered over 2.19M docids touches essentially every sidecar page —
~2.2M doc-decodes to score 10,875 postings, a ~200x amplification.

**Fix (in this build): decode only the covering 128-doc block.** Walk the page's
block *headers* (first_docid/count/gapbytes — no FOR-unpack) to find the block
containing the sought docid, then unpack that one block. Same page read, ~31x
less decode work. No format change, no REINDEX, no effect on count/AND/prefix.

| band       | 1.5.8 | + block-granular | change |
|------------|-------|------------------|--------|
| rare  k10  | 10.2  | **6.05**         | **1.7x faster** |
| mid   k10  | 11.3  | 10.84            | ~flat |
| common k10 | 60.9  | 56.5             | 1.08x |
| count/AND/prefix | 2.35/0.88/2.28 | 2.34/0.87/2.41 | unchanged |

Parity PASS after the change. Mid barely moves because `hungary`'s 24k postings
are dense enough (~1 per 91 docids) that consecutive postings often share a
block, so the whole-page decode was already amortized — the win is specifically
for sparse/scattered terms.

## Where that leaves us

- **Smallest index** (1421 MB, 2.1x smaller than pg_search/vchord).
- **Fastest count (5.9x) and AND (3.8x)** vs pg_search; the two ranking-only
  engines cannot answer those from the index at all.
- **Exact top-k, verified** — the only engine here with that guarantee.
- **Still slower on ranked latency**, and the remaining gap is now cleanly
  attributed: (a) we must score every posting (information-theoretic for a
  docid-ordered layout), and (b) on the common band we are additionally scoring
  ~48% more postings than pg_search because we stem and it does not.
- Honest framing for the common band: comparing 56.5 ms against 2.19 ms compares
  a stemmed 734k-posting scan against a literal 495k-posting scan. Normalizing
  for posting count still leaves pg_fts ~17x slower, so the gap is real — but
  it is 17x, not 26x, and we return the better answer.
