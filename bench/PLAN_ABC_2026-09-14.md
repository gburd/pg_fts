# Plan: A / B / C from the TIN feasibility note

**Date:** 2026-09-14 · Written before implementing, per the "read fully, then be lazy" rule.

## What the code review changed about the plan

Reading the actual paths before writing anything moved all three items:

### B — **already implemented.** Scope shrinks to testing.

`bm25_count_dictdf_fastpath()` (`pg_fts_am_scan.c`) already counts a single plain term from
`Sum(df)` with no posting decode and no heap probe, behind exactly the four gates my note
said were required:

| gate | check |
|---|---|
| one plain positive term | `q->nitems == 1`, `FTS_QI_VAL`, no PREFIX/FUZZY/REGEX/WEIGHTED |
| no pending docs | `meta.npending == 0` |
| no tombstones | `ndeleted == 0 && livedocslen == 0` for every segment |
| heap fully all-visible | `VM_ALL_VISIBLE` over every heap page |
| plus a generation re-check | guards concurrent merge |

So my feasibility note was wrong to list B as work to do. **The gap is test coverage:** one
positive case in `sql/pg_fts.sql` (`big_fastpath`) and *nothing* asserting the gates
actually refuse. A fast path that silently returns a wrong count when a gate is missed is
the worst failure shape available, and right now nothing would catch it.

**Work:** tests only — each gate proven to fall back, and every fallback proven to agree
with the slow path.

### A — **valid, and bigger than described.** Two per-TID costs, not one.

`bm25_count_visible()` loops over matches doing `VM_ALL_VISIBLE(heap, blk, &vmbuf)` **per
TID**, and on a not-all-visible page it also does `table_slot_create()` +
`ExecDropSingleTupleTableSlot()` **per TID**.

Premise verified: `tidset_sort_uniq()` does `qsort(cmp_tid)` + dedup, and
`docid = block × MaxHeapTuplesPerPage + offset` is monotonic in (block, offset), so **all
matches on one heap page are a strictly contiguous run**.

**Work:** hoist both. Track `lastblk` so the VM is consulted once per *block run*, and
create the tuple slot once per call instead of once per TID. Pure code change, no format
change, no behaviour change.

### C — **do not do it.** The premise does not hold.

My note claimed a merge could "copy a term's posting bytes verbatim" when one source segment
holds the term untombstoned. Reading `bm25_merge_segments_streaming()`: the merge decodes
each source term with `bm25_decode_term()` and feeds every posting through `add_posting()`
into a build hash table, which is re-encoded at segment flush. There is **no byte-stream
splice point** — the output encoding is produced by the builder, and the per-posting path
also feeds the doclen sidecar (`doclen_collector_add`) and re-quantizes doclen from a v4
source. A verbatim copy would have to bypass all of that and reproduce the builder's exact
output framing.

That is a large, high-risk change to the one code path that has already produced a P0
(non-terminating VACUUM) and two crash fixes this line. The honest call is that C as
written was a guess about code I had not read closely enough. **Dropping it**, and recording
why, rather than half-building it.

## Deliverables

1. **A:** block-run VM checking + hoisted slot in `bm25_count_visible()`.
2. **B:** gate-refusal tests for the existing df fast path.
3. **C:** withdrawn, with the reason recorded in the feasibility note and ROADMAP.
4. Docs (README + SGML) for the counting behaviour, CHANGELOG, release.

## Correctness bar

`fts_count()` must return **exactly** what the slow path returns, under every gate
combination. Both A and B are pure optimisations of a counting path: any divergence is a
wrong answer to `SELECT count(*)`, which is the least forgivable bug class in this project.
Every test therefore compares against a ground-truth count computed a different way.
