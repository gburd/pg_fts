## sparsemap 5.9.0 against what pg_fts stores

5.9.0's `sm_open` drops empty chunks from an older stream before validating.  On a
tombstone blob 5.8.5 wrote, that would shrink the map, and `bm25_sm_open_checked`
would report it corrupt.  `data_180_2026-11-19/smdiff/` builds tombstone maps the way
`bm25_bulkdelete` does: `sm_create`, then a sorted `sm_add_many_grow` per VACUUM round,
1-4 rounds, with docid = blk * 291 + off.  It covers six shapes: dense, sparse, half,
1/80, a contiguous block range and random density.  Each map was serialized by 5.8.5
and opened by 5.9.0 exactly as pg_fts opens it.  Across 2,000 maps (8 seeds x 250):

- 0 size or `sm_validate` changes;
- 0 membership differences, comparing:
  - `sm_contains` with an ascending cursor and without;
  - the full `sm_next_member` walk;
  - cardinality and maximum;
  - non-members next to members.

In place, the release gate's upgrade (below) builds tombstones on 1.17.0 and then reads
them on 1.18.0.  The checks pass on PG 17, 18 and 19, on x86_64 and aarch64:

- `fts_index_segments().ndeleted` 2000 as written;
- `count(w7)` equal to the heap.

**CBMC** (`test/cbmc/smcursor_harness.c`, which includes `vendor/sm.c`; local, cbmc
6.10, 19 min 43 s):

- the layouts 5.9.0 serializes are byte-identical to `smcursor_layouts.h`;
- C1-C4 PASS on all four layouts;
- the stale-offset mutant (no start-word check) FAILs as it must.

**Fuzz** (`test/fuzz/run.sh`): `== ALL CLEAN ==`, every teeth case aborting as
expected.

## A/B: sparsemap 5.8.5 vs 5.9.0 in pg_fts (c6id.metal, PG 18.7)

The script is `data_180_2026-11-19/ab180.sh` and the log `ab180.log`.

**State.** 1.9M rows (40-160 tokens, log-uniform 200k vocabulary) under
`doclen_sidecar = off`, packed into one segment.  Then 1/80 of the rows were deleted
and VACUUMed, leaving 23,750 scattered tombstones.  Every ranked and count lookup
there consults the tombstone sparsemap.

**Host.** Turbo off, performance governor, THP never, server pinned to node 0.

**Arms** (the `.so` swapped on one index):

- **1.17.0**: the v1.17.0 PGXN zip, sha-checked;
- **A/A**: the same zip built again;
- **sm590**: 1.17.0 with only `vendor/sm.{c,h}` from 5.9.0;
- **1.18.0**: the release branch.

**Correctness first.**  The top-10/200 ids of `patch`, `vacuum` and `remove`, and
`count(*)` of `remove` (112,770), are identical on all four arms.

**Ranked and count latency.**  Each value is the median of 12 samples; each sample is
one psql session's median of 11 after 3 warm runs, over 6 ABBA rounds:

| query | 1.17.0 ms | A/A | sm590 ms | 1.18.0 ms | 1.18.0 vs 1.17.0 |
|---|---:|---:|---:|---:|---:|
| `patch`, ranked top-10 | 1.893 | -0.24% | 1.301 | 1.299 | -31.4% (1.46x) |
| `vacuum`, ranked top-200 | 4.724 | +0.07% | 3.755 | 3.758 | -20.5% (1.26x) |

The samples did not overlap: for every query, the fastest 1.17.0 sample was slower than

## The autovacuum abort (ROADMAP I33)

`t/006` lost its server on the first TAP run against an assert-enabled 19.0:

```
TRAP: failed Assert("pgstat_tracks_io_op(MyBackendType, io_object, io_context, io_op)"), File: "pgstat_io.c", Line: 66
  ... StartReadBuffer <- ReadBufferExtended <- pg_fts.so <- index_bulk_delete <- ... AutoVacWorkerMain
autovacuum worker (PID ...) was terminated by signal 6: Aborted
```

pg_fts's maintenance ring was `BAS_BULKWRITE`, and `pgstat_tracks_io_object()`
excludes bulk-write I/O for autovacuum workers in 17, 18 and 19 alike.  The same TAP
file fails on an assert-enabled 17 with 1.17.0, so this was not a 19 change.  No earlier
gate had run TAP on an assert-enabled server: the gate builds were `-O2` without
asserts, the ASan build ran only `asan_smoke.sql`, and the local runs had autovacuum
off.

**The fix:** autovacuum workers get `GetAccessStrategyWithSize(BAS_VACUUM, 16 MB)`.

**Checks:**

- **New test.** `t/008` now triggers an autovacuum of an fts index, then checks the log
  for a terminated worker and the index against the heap.  It fails on 1.17.0 with
  assert-enabled 17 (exit 29, 1 TRAP) and passes with the fix on assert-enabled 17
  and 19.0.
- **Locally.** Every TAP file and the hook TAP files pass on assert-enabled 19.0 with
  0 TRAPs.  The regression suite passes with autovacuum on, on assert-enabled 17.
- **The gate** now runs an assert-enabled 19.0 pass.
