## VACUUM growth when the truncation is declined (fts blocks)

`bug2e-*.out` (PG 18.6; C = CREATE INDEX CONCURRENTLY, 60k rows; D = the
`vacuum_parallel` layout; E = C with a reader holding AccessShareLock on the index across
each serial VACUUM):

| scenario | 1.10.0 | 1.13.0 | 1.14.0 | 1.14.1 |
|---|---|---|---|---|
| C, 3 parallel VACUUMs, then serial | 1506 -> 686 686 688 -> 690 | ERROR x3 -> 690 | 1508 -> 2742 3417 4085 -> 664 | 1505 held -> 686 |
| D, 3 parallel VACUUMs, then serial | 7848 -> 799 799 799 -> 799 | ERROR x3 -> 799 | 7848 -> 8632 9415 10198 -> 755 | 7845 held -> 799 |
| E, 3 serial VACUUMs with a reader, then alone | 1505 -> 686 686 688 -> 690 | 1507 -> 2742 3417 4085 -> 664 | 1506 -> 2742 3417 4085 -> 664 | 1506 held -> 686 |

Second scale, 600,000 rows, CIC build, PG 18.6 (`scale-v140.out`, `scale-final.out`;
the load's own `VACUUM ANALYZE` is parallel, which is why the start sizes differ). Live
size is about 5,930 blocks (`scale2.out`):

| scenario | 1.14.0 | 1.14.1 |
|---|---|---|
| reader holds a lock across 3 serial VACUUMs, then 2 alone | 23709 -> 29634 35558 41480 -> 5929 5929 | 14066 held -> 5956 5958 |
| 3 parallel VACUUMs, then 2 serial | 23709 -> 29634 35558 41480 -> 5929 5929 | 14097 held -> 5956 5958 |

Each declined VACUUM on 1.14.0 adds 5,925 blocks, about the live size. With no reader
and no parallelism (`scale2.out`), 1.10.0, 1.13.0, 1.14.0 and 1.14.1 behave identically:
14,062-14,117 after CIC, 5,928 after the first VACUUM, 5,940 after a delete + VACUUM.

1.10.0 shrinks because it truncated without a lock (the 1.11.0 fix ada32aa made the
truncation conditional because that was unsafe). Reporter's own Bug-2 steps
(`bug2d-final.out`, 1.10.0 parallel-built index, upgraded in place, 4 parallel VACUUMs):
1.13.0 ERROR x4; 1.14.0 494 -> 923 -> 1150 -> 1374 -> 1597; 1.14.1 494 held, serial 233.
On the reporter's steps with a serially built index (`bug2.out`, `bug2b.out`) no arm
fires: the file has no free tail, so the truncation is never attempted.
