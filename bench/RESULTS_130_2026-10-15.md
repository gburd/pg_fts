# Results: 1.13.0 vs 1.12.1 (2026-10-15)

1.13.0 is GitHub PR #12 (Jim Dawdy) ported onto 1.12.1, plus the follow-ups that the
port turned up.  The CHANGELOG has the full list.  This file records the release
qualification and the A/B run.  Every run was on Debian 13 EC2 hosts in the kiwi
account; none ran on a workstation.

## Gate

The gate ran on c6id.4xlarge (x86_64) and c7gd.4xlarge (aarch64), with PG 17.10 and
PG 18.1 built from source.  On each host it covered:
- regress and isolation;
- `test/query_binary.py` (49 cases);
- every TAP test, plus `t/012` three more times;
- `ci/check-alloc.sh`, `make check-ascii` and `test/fuzz/run.sh`.

Results: all green on the final tree 997da9c, and no OOM events.  Logs:
`data_130_2026-10-15/gate_final_g13{x,a}.txt`.

The first gate on the port (2cceb2a) failed `t/012` on both hosts: its readers were
OOM-killed at 16 GB each.  The cause was an O(n^2) pending-list collect, present in
every release.  PR #12 exposed it by making ranked scans read the pending list.  Logs:
`gate_g13{x,a}_2cceb2a_t012_oom.txt`.  Fixed in c927d12.  `pendmem2.sh` measures one
backend: 32k pending matches took 2.6 s and 3 GB on 1.12.0, and 5.4 ms with no
measurable growth after the fix.

The upgrade from 1.12.1 (PGXN zip) to 1.13.0 in place passed `ok=113 bad=0`
(`upgrade_qual_1.12.1_to_1.13.0.txt`).

#11 (deep ranked pull) was rerun with PR #12's own fixture (`deep.sql`: 2 segments,
2,000 matches, 10% deleted and re-inserted).  On both 1.12.1 and 1.13.0 the pull
returned 2,000 rows and 2,000 distinct ids, and every LIMIT prefix was consistent.

## A/B (`ab13f.sh`)

Setup:
- One c6id.4xlarge host, PG 17.10.
- 2M rows on a `positions = on` expression index: 188 MB, one segment.
- One data directory; the two `.so` builds were swapped between rounds, over 3
  alternating rounds.
- Each figure is the median of 9 timed runs inside one psql session (12 run, the
  first 3 dropped); the table gives the median across rounds and the min-max range.
- Correctness was checked first for all 10 queries: top-10 ids and `@@@` counts were
  identical, and every count was non-zero.

| query | ranked 1.12.1 | ranked 1.13.0 | bitmap count 1.12.1 | bitmap count 1.13.0 |
|---|---|---|---|---|
| `rare` | 4.5 | 4.4 | 71.5 | 69.4 |
| `common` | 18.9 | 18.8 | 155.3 | 157.8 |
| `rare & w5` | 2.2 | 2.1 | 9.2 | 9.2 |
| `w1 \| w2 \| w3 \| rare` | 3.2 | 3.3 | 76.8 | 75.6 |
| `"hot dog"` | 16.9 | 16.7 | 68.1 | 69.5 |
| `common & !w3` | 6.7 | 6.7 | 2,156.9 | 162.4 |
| `"hot dog" & w7` | 34.3 | 37.2 | 30.2 | 34.1 |
| `rare & !"hot dog"` | 9,470.0 | 142.5 | 9,286.6 | 157.7 |
| `w5 & !"hot dog"` | 9,448.8 | 39.7 | 9,301.6 | 49.5 |
| `w5 \| "hot dog"` | 1,635.3 | 83.3 | 1,610.6 | 117.6 |

Each A/B round's min-max is in `ab_121_vs_130_final.txt`.

Host memory chase (mbench2, 4 GiB with THP): 111.9 ns before the run and 120.6 ns
after.  Same host and same order for both arms, so this does not bias the comparison.

Regression: `"hot dog" & w7` was 8% slower ranked and 13% slower as a count.  The
candidates (1,874) now go through the positional span matcher instead of the heap
recheck, and decoding `w7`'s positions costs more than the recheck at this size.  This
was not fixed in 1.13.0.  Tried and reverted: decoding only the TIDs of a term that
sits outside every proximity operator.  It was not measured as a full A/B arm.  One
build ran 37.5 ms for this query (7 runs), and perf showed `bm25_decode_term` still
dominating through `bm25_lookup_term_pos`.  The cost is in the phrase terms'
positional decode, not in `w7`'s.  Unmeasured, therefore, whether any change here
would close the gap.

Two intermediate measurements, kept in `ab_121_vs_c927d12_first.txt` and
`ab_lazygate_check.txt`, found two regressions in the first port, both fixed in 997da9c:
- **Ranked `"hot dog"` 16.9 -> 29.8 ms.**  Quoted phrases became exact `<->`, which
  the lazy phrase gate refused.
- **`w5 & !"hot dog"` still took 2.2 s.**  The candidate set was the whole segment.
