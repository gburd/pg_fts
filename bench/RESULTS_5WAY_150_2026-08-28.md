# 5-way BM25 comparison — pg_fts 1.5.0 vs the field (2026-08-28)

Same corpus, same instances, same harness as the earlier 4-way/5-way runs, now
with **pg_fts 1.5.0** (per-segment doclen sidecar, format v4).

## Rig
- EC2 r6id.4xlarge (mala), PostgreSQL 17.10, local NVMe, `shared_buffers=64GB`,
  prewarmed. One dedicated instance per engine.
- Corpus: wikimedia/wikipedia 20231101.en, first **2,188,038** articles, body
  column. Heap 1744 MB on every host (identical corpus).
- df bands: rare=slovakia (~10.9k), mid=hungary (~24k), common=year (~735k),
  AND=slovakia&hungary. NSAMP=200 warm `\timing` samples -> median/p99 (ms).
- Engines: pg_fts 1.5.0; Timescale pg_textsearch; ParadeDB pg_search (Tantivy);
  VectorChord-bm25. pgts and vchord are ranking-only (no boolean/count/phrase).

## pg_fts 1.4.0 -> 1.5.0 on THIS corpus (the sidecar effect, real Wikipedia)

| band        | 1.4.0 | 1.5.0 | change |
|-------------|-------|-------|--------|
| rare  k10   | 4.4   | 5.0   | ~flat (noise; heap-recheck bound) |
| mid   k10   | 5.7   | 5.4   | ~flat |
| common k10  | 28.6  | 14.1  | **2.0x faster** |
| common k100 | 30.0  | 20.6  | 1.5x faster |
| index size  | 2089 MB | 1414 MB | **32% smaller** |

NOTE on the earlier synthetic-rig claim: the synthetic 2M corpus showed common
k10 7.7x faster (17.5->2.3 ms).  On REAL Wikipedia the win is **2.0x** (28.6->14.1
ms).  The synthetic corpus's more-uniform doclen made the per-posting doclen
decode a larger fraction of scan cost than real text does, so it overstated the
gain.  The real, defensible numbers are here: 2x common-term latency + 32%
smaller index.

## Build time + index size

| engine        | build | index size |
|---------------|-------|------------|
| pg_fts 1.5.0  | 179 s | **1414 MB** |
| pg_textsearch | 263 s | 1885 MB    |
| pg_search     | 45 s  | 2332 MB    |
| vchord        | 41 s  | 2906 MB    |

pg_fts is now the **smallest index** of the four (1414 MB), was mid-pack at 1.4.0
(2089 MB).  The Rust engines (pg_search, vchord) build ~4x faster (Tantivy /
pgrx parallel build); pg_fts and pg_textsearch are single-threaded-ish C builds.

## Correctness cross-check
All engines return the same-magnitude match counts on the shared corpus
(slovakia ~10.9k, hungary ~24k). pg_fts ranked top-k parity vs exact BM25 PASSes
within the documented v4 quantization bound (see bench/parity_check.sh).

## Honest read

- **Size**: pg_fts 1.5.0 wins (smallest, 1414 MB), a real 1.5.0 gain.
- **Common-term ranked**: 1.5.0 halved it (28.6->14.1 ms) and drew LEVEL with
  pg_textsearch, but pg_search (Tantivy) is still ~3x faster (4.5 ms) and vchord
  ~2x (6 ms).  The Tantivy columnar codec still decodes less per candidate; a
  further pg_fts win there is the (deferred) impact-quantized-postings work,
  which prior measurement showed does not prune real text well -- so this gap
  may be structural to a docid-ordered index.
- **rare/mid**: pg_textsearch is fastest (~3.3 ms); pg_fts (5 ms) and pg_search
  (4.3 ms) are close; the pg_fts rare number is heap-recheck-bound and unchanged
  by the sidecar.
- **Features**: pg_fts remains the only engine with fast count(*) (3.4 ms vs
  pg_search 16 ms), boolean AND (2.5 ms), phrase (2.3 ms), and prefix (1.7 ms) --
  pg_textsearch and vchord are ranking-only and cannot do these at all.

Bottom line: 1.5.0 makes pg_fts the smallest index in class and closes the
common-term ranked gap to pg_textsearch (from 2x behind to level), while keeping
its unique feature breadth.  It does not overtake Tantivy on pure common-term
ranked latency -- that remains pg_search's advantage.
