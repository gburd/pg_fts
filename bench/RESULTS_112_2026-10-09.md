# 1.12.0 release qualification and I7 A/B (aarch64 Debian, 2026-10-09)

Plan: `bench/PLAN_I7_2026-10-09.md` (ef756fc, written before the code).  Cause the change
addresses: `bench/RESULTS_TPS_VARIANCE_2026-10-09.md`.  Data: `bench/data_i7_2026-10-09/`
(first A/B, commit 579a9f4, hosts h1-h4) and `bench/data_112_2026-10-09/` (the release
tree 389a610, hosts f1-f2; the aarch64 gate, churn, race and upgrade check in
`release/`).  Tables are recomputed by each directory's `summarize.py`.

Arms: **1.11.0** as released (PGXN zip, binary `da915fc2`) and **I7** (579a9f4, then the
release tree 389a610, binary `b3d4b769`).  Same host, same data directory and index files
(built by 1.11.0; no format change), alternating.  Six fresh r7gd.4xlarge, Debian 13
arm64, PG 17.10, the 2.19M-article corpus and settings of every earlier run.  The host
state is recorded before and after (1 GiB 4 KiB-page pointer chase): h1, h2, f1 fast
(142-159 ns); h3, h4 slow (195-236 ns); f2 changed from fast (149) to slow (205) during its
run.

## Correctness (before any timing)

- Identical ranked ids and index scores (`fts_search`, 9 decimals) on all 11 ranked bands
  and identical `count(*)`, both arms, on all six hosts (`*/gate_*.txt`).
- The release tree passes the full gate: x86 nix installcheck (13 + 2) and TAP (9 files,
  104 tests) on pg17 and pg18; aarch64 fuzz ALL CLEAN, regression 13/13 (with the new
  `dict_dir`), isolation 2/2, TAP 12 files / 137 tests, coverage 91.2 / 96.9 / 73.0
  (`release/gate_aarch64_q12.txt`).
- Concurrency (`release/gate_aarch64_q12.txt`): churn (8 writers + ranked/count readers +
  VACUUM and `fts_merge`, 300 s) twice -- 3.16M and 3.19M writes, 0 failed, every count
  exact, 0 non-matching rows, 0 hard errors; race (8 inserters + `fts_merge` every 0.2 s,
  40 s) three times -- heap == truth == pushdown == bitmap, 0 missing.
- In-place upgrade from an index built by released 1.11.0 (tombstones, positions on), on
  the same data directory: 113 checks, 0 bad, through 1.12.0 binary on 1.11.0 SQL,
  `ALTER EXTENSION UPDATE`, writes + merge + `fts_vacuum`, and REINDEX; cached dictionary
  lookup == page-chain lookup on the upgraded index (`release/upgrade_qual_111_to_112.txt`).

The 6 vs 6 points separate on every band and host except `count(*)` and, on f2 (which
changed state mid-run), `united & states` at 16 clients (+47% median, overlapping); f2's
other bands follow the pattern (rare c16 +74%, c64 +95%).

Why it is larger than the buffer count suggests: the removed reads are on the pages every
concurrent query shares (the dictionary-index chain), so each saved read is a contended
buffer-header atomic and content-lock round trip, not just a page access.  On fast h1,
per-transaction core time at 16 clients fell from 602 to 344 us (rare) and from 727 to
386 us (common); a perf profile at 16 clients (`data_i7_2026-10-09/h1/profile_rare_c16.txt`)
shows `bm25_dict_seek` -- 37% of all samples with 1.11.0 -- gone, and the doclen lookup and
scoring as the largest remaining costs.

## Memory

The relcache chunk holds the directory once per backend and segment-directory
generation: `CacheMemoryContext` 540 kB -> 1.4 MB per backend on the 2.19M index (one
backend after one ranked query), within the 64 MB `pg_fts.doclen_cache_mb` default.  The
build is a walk of the 85-page index chain, done once per backend per generation.

## What this does not show

- x86, other instance types, network storage: not measured.  The mechanism (fewer reads of
  shared pages) is not aarch64-specific; the size of the gain on other hardware is
  unmeasured.
- Indexes with many segments: the A/B ran on single-segment indexes (the state after a
  build); `dict_dir` and the upgrade check cover several segments for correctness only.
