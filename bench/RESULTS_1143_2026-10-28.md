## 2. #6 timings (`b6/`)

The reporter's 400,000-row corpus, made deterministic with `setseed(0.6)`
(`b6/setup6.sql`; corpus md5 `ad0a4c44...` in all four clusters; 100,266 apple, 100,248
banana, 1 segment).  Ranked top-10 through a prepared statement with seq and bitmap scans
off.  Each query is run warm 21 times per run (median taken), 3 runs per arm.  Before any
timing, all four arms' top-10 id lists were compared and are byte-identical
(`b6/runs/run_*_1.out`, CORRECTNESS section).  Both clusters were created with
`CREATE EXTENSION` at 1.14.2, before the version bump; only the `.so` differs.

Median of the three run medians, ms (each run's median is in `b6/bench6.log`):

| query | PG17 1.14.2 | PG17 1.14.3 | PG18 1.14.2 | PG18 1.14.3 |
|---|---|---|---|---|
| `zzzq & (apple \| banana)` | 10.826 | 0.066 | 10.700 | 0.067 |
| `zzzq & apple` | 0.065 | 0.064 | 0.067 | 0.066 |
| `rare & apple` | 0.076 | 0.075 | 0.078 | 0.077 |
| `rare & (apple \| banana)` | 3.626 | 3.624 | 3.560 | 3.655 |
| `apple \| banana` | 7.774 | 7.721 | 7.621 | 7.987 |
| `zzzq & (apple \| ban:*)` | 3.205 | 3.184 | 3.183 | 3.195 |
| `zzzq & ban:*` | 0.912 | 0.901 | 0.898 | 0.900 |

Index buffers, `zzzq & (apple | banana)`: 1,581 -> 13 (EXPLAIN BUFFERS, both majors).

**The PG18 `apple | banana` (+4.8%) and `rare & (apple | banana)` (+2.7%) differences are
not the change.**  `apple | banana` is pure OR, so it takes neither gate and never reaches
`bool_gate_may_admit`.  `b6/swap6.log` runs each PG18 cluster with each `.so`, 3 runs
each.  Pure-OR medians are 7.60-8.19 ms with the 1.14.2 `.so` and 7.73-8.23 ms with the
1.14.3 `.so`; the ranges overlap.  `rare & (apple | banana)` gives 3.565-3.724 vs
3.614-3.797, which also overlap.  The two builds' run-to-run variation is larger than
the difference.  The `zzzq & (apple | banana)` gap holds in every combination
(10.69-11.33 vs 0.067-0.069).

## 3. `vacuum_parallel` flake (ROADMAP I18; `flake/`)

The nix PG17 gate failed `vacuum_parallel`'s `serial_reclaims` size check once on this
tree (before: 1 of 26 runs for 1.14.2).  The size check is
`pg_relation_size < s0 / 2` after two non-parallel VACUUMs.  A freed page is recycled
only once `GlobalVisCheckRemovableXid` says no snapshot can still see it
(`bm25_page_recyclable`), so a snapshot held by another backend, even in **another
database**, keeps the file large.  That reproduces the failure every time (below).  The
likely source in the nix run is an autovacuum worker: the derivation's cluster has
autovacuum on, and only `vp` turns it off.  This was not confirmed in the failing nix run
itself, whose log does not record autovacuum activity.

| PG17 fix build, `flake/vpexp.sh` | serial_reclaims |
|---|---|
| no other snapshot | t, t, t |
| REPEATABLE READ snapshot held open in `postgres` for the whole test | f, f, f |

The test now waits, with a 60 s bound, until no other backend has a `backend_xmin`
before each non-parallel VACUUM.  `flake/vpexp2.sh` runs the new test against the new
expected file, pg_regress style:

| arm | PG17 | PG18 |
|---|---|---|
| no holder (x2) | pass, pass (6.3 s) | pass, pass (6.4 s) |
| holder for 20 s (x2) | pass, pass (19.4 s) | pass, pass (19.4 s) |
| holder for 300 s | fail at the bound (127.6 s) | fail at the bound (127.6 s) |

The last row shows the check still fails a VACUUM that does not reclaim.
