regression test added for each one fails on 1.14.2 (`repro/*_on_v1142.txt` are those

duplicated row (section 5) is a known issue.  #6 (a performance report, not a wrong result) is fixed only for the case
it describes, an AND operand with no postings; the general case is ROADMAP I19a/I19b.

## 2. #6 timings (`b6/`)

The reporter's 400,000-row corpus, made deterministic with `setseed(0.6)`
(`b6/setup6.sql`; corpus md5 `ad0a4c44...` in all four clusters; 100,266 apple, 100,248
banana, 1 segment).  Ranked top-10 through a prepared statement with seq and bitmap scans
off.  Each query is run warm 21 times per run (median taken), 3 runs per arm.  Before any
timing, all four arms' top-10 id lists were compared and are byte-identical
(`b6/runs/run_*_1.out`, CORRECTNESS section).  Both clusters were created with
`CREATE EXTENSION` at 1.14.2, before the version bump; only the `.so` differs.

| `zzzq & (apple \| banana)` | 10.826 | 0.066 | 10.700 | 0.067 |
| `zzzq & apple` | 0.065 | 0.064 | 0.067 | 0.066 |

**The PG18 `apple | banana` (+4.8%) and `rare & (apple | banana)` (+2.7%) differences are

## 3. `vacuum_parallel` flake (ROADMAP I18; `flake/`)

The nix PG17 gate failed `vacuum_parallel`'s `serial_reclaims` size check once on this
tree (before: 1 of 26 runs for 1.14.2).  The size check is
`pg_relation_size < s0 / 2` after two non-parallel VACUUMs.  A freed page is recycled
only once `GlobalVisCheckRemovableXid` says no snapshot can still see it
(`bm25_page_recyclable`), so a snapshot held by another backend, even in **another
database**, keeps the file large.  That reproduces the failure every time (below).  The
likely source in the nix run is an autovacuum worker: the derivation's cluster has
autovacuum on, and only `vp` turns it off.  This was not confirmed in the failing nix run
itself, whose log does not record autovacuum activity.

| PG17 fix build, `flake/vpexp.sh` | serial_reclaims |
|---|---|
| no other snapshot | t, t, t |
| REPEATABLE READ snapshot held open in `postgres` for the whole test | f, f, f |

The test now waits, with a 60 s bound, until no other backend has a `backend_xmin`
before each non-parallel VACUUM.  `flake/vpexp2.sh` runs the new test against the new
expected file, pg_regress style:

| arm | PG17 | PG18 |
|---|---|---|
| no holder (x2) | pass, pass (6.3 s) | pass, pass (6.4 s) |
| holder for 20 s (x2) | pass, pass (19.4 s) | pass, pass (19.4 s) |
| holder for 300 s | fail at the bound (127.6 s) | fail at the bound (127.6 s) |

The last row shows the check still fails a VACUUM that does not reclaim.

## 4. Ranked-scan crash under frequent flushes (`race/`; fixed)

Found while reproducing the review's duplicate-row finding (section 5).  The setup
(`race/dstress.sh`) uses a 2,000-row base table, 8 sessions inserting single rows with
`pg_fts.pending_flush_threshold = 20` (an inline flush every 20 documents), and 8
sessions running ranked `LIMIT 10` and `LIMIT 1000` queries.

| build (`race/dsrate.out`, 5 runs each) | PG 17.10 | PG 18.6 |
|---|---|---|
| 1.14.2 | crashed 2 of 5 | crashed 3 of 5 |
| 1.14.3 tree before the fix | crashed 5 of 5 | crashed 4 of 5 |

Every core has frame 0 in `bm25_topk_visible` at `cand[i].tid`, with `cand = 0x0` and
`ncand = 4000` (`race/core_frame0_pg17_fix.txt`).  The generation retry ran out, the
last attempt freed `cand`, and `ncand` kept its value.

Fix: keep the last attempt's candidates after the cap.  `t/013_ranked_flush_race.pl`
runs the same race under pgbench (`race/t013ab.log`):

| `.so` | PG 17.10 | PG 18.6 |
|---|---|---|
| 1.14.2 | FAIL 3 of 3 (a backend terminated by signal) | FAIL 3 of 3 |
| fix (7f233ca) | PASS 3 of 3 | PASS 3 of 3 |

The fixed build gave 0 crashes in 10 more runs of the stress setup (`race/duprate.log`).

## 5. Duplicate rows in the flush publish window (`dup/`; known issue, ROADMAP I20)

The finding was made by the review, from reading the code.  A flush publishes its
segment (generation + 1) and clears the pending list (generation + 1) in two metapage
updates.  A ranked scan whose whole candidate pass falls between the two sees each
flushed document twice.

**With gdb** (`dup/dup.sh`): 200 rows sit in a segment and 50 `fresh` rows are pending.
`fts_merge` is stopped right after `bm25_add_segment_with_room` returns, and a second
session runs `dup/dup_probe.sql`:

| probe | in the window | after the flush |
|---|---|---|
| ranked `fresh`, LIMIT 1000: rows / distinct ids | 100 / 50 | 50 / 50 |
| ranked `fresh`, LIMIT 10: rows / distinct ids | 10 / 5 | -- |
| `fts_index_stats().ndocs` | 300 | 250 |
| `fts_search` rows / distinct ctids | 100 / 50 | 50 / 50 |
| `count(*) ... @@@ 'fresh'` | 50 | 50 |
| prefix `fre:*` ranked rows / distinct (heap-pass path) | 50 / 50 | -- |
| `fresh & apple` ranked rows / distinct | 100 / 50 | -- |
| `apple` ranked rows / distinct | 300 / 250 | 250 / 250 |

The same results come from 1.14.2 on PG 17.10 and from 1.14.3 on PG 18.6
(`dup/probe_mid_*.out`).  In the window, `fts_index_df` reads `{100,300}` on 1.14.3,
because it counts pending documents, and `{50,250}` on 1.14.2.  The count path is
correct because it removes duplicate TIDs.

**Without a debugger**, on the crash-fixed build (`race/duprate.log`, 10 runs over the
two majors): 25 of 24,000 ranked `LIMIT 1000` queries returned a row twice, and 0 of
24,000 `LIMIT 10` queries did.  The fix (one metapage update) changes the flush, so it
is not in this point release.
