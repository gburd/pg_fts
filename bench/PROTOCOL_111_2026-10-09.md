# 1.11.0 release benchmark protocol (aarch64 Debian, 2026-10-09)

Written BEFORE the run, so the method cannot be fitted to the results.  It is the
Approach A protocol (`bench/PROTOCOL_A_2026-10-07.md`, itself the 1.10.0 protocol plus
four additions) with the changes listed below.  Every rule in both applies here.

## Why this run

`bench/RESULTS_A_2026-10-07.md` measured commit 39b6a42.  The 1.11.0 release (tag
v1.11.0 = 93c4b5f) adds the VACUUM pending-delete fix and four concurrency fixes after that
commit (CHANGELOG 1.11.0).  They touch the write, flush, page-free and truncate paths, not the
query traversals, but the release binary itself has not been timed.  This run times it, and
re-measures every competitor on fresh hosts the same night.

## Questions

1. What are the release binary's numbers on every band of the Approach A protocol?
2. Did anything move between the benchmarked commit 39b6a42 and the release?  A/B on one
   host, same index files, alternating, as the Approach A protocol's pg_fts A/B.
3. Where does pg_fts 1.11.0 stand against pg_textsearch, pg_search and VectorChord-bm25 as
   they ship on 2026-10-09?

## Setup (unchanged)

EC2 r7gd.4xlarge (Graviton3), Debian 13 arm64 (`debian-13-arm64-20261001-2618`), PG 17.10
from source with identical flags on every host, `shared_buffers=32GB`, `work_mem=256MB`,
`maintenance_work_mem=8GB`, `jit=off`, `autovacuum=off` during measurement,
`max_connections=200`; the same 2,188,038-article Wikipedia corpus (TSV md5 `f5939e85...`
checked); each engine's documented English-stemmed setup; one host per engine.

## Changes from the Approach A protocol

1. **Arms.**  The pg_fts host's two arms are the **1.11.0 release** built from the PGXN zip
   (sha256 `fff822fe...`, verified on the host before building) and **39b6a42** (the binary
   RESULTS_A measured).  The 1.10.0 arm is dropped: it was measured in RESULTS_A on this rig,
   and those numbers stand.
2. **Build of record is the release.**  The expression-index build, the stored-column builds
   (positions off/on) and the sizes are measured with the release binary.  The 39b6a42 arm
   builds too (both arms build each index once, release first), so a build-time difference
   between the arms can be read against the run-to-run spread; the measured indexes are the
   ones the release built, and both arms read them.
3. **Engine versions.**  Latest release of each on 2026-10-09: pg_textsearch **v1.5.1**
   (unchanged), **pg_search 0.26.1** (released 2026-10-08; official `trixie_arm64` .deb for
   PG17, with pgvector 0.8.7 and libopenblas0 as for 0.26.0), VectorChord-bm25 **0.3.0** with
   pg_tokenizer **0.1.1** (unchanged).  pg_search moving from 0.26.0 to 0.26.1 is a
   version change and is reported as one, not as noise.
4. **Correctness gate for the A/B** is the Approach A gate unchanged (both arms: same ids
   and index scores within 1e-9 on every band, and the count).  No band is expected to
   differ; any difference stops the timing for that band and is reported.  The exhaustive
   oracles (`mt_oracle.py` for the 4-term OR, `and_oracle.py` for AND and phrase) are run
   on the release arm.
5. **Throughput** for every engine is the settled form (`tps2.sh`: CHECKPOINT, sync, 60 s
   idle, prewarm, 10 s warm-up at 8, then 16/32/64 clients x 30 s x 2 passes), run twice
   per engine.  RESULTS_A tabled settled numbers for pg_fts and in-run numbers for the
   others; this run tables the settled form for all four.  The in-run measurement is kept
   in the raw data.
6. **Concurrent-write band (new, reported separately, not in the scoreboard).**  The
   release's changes are on the write path, so on the pg_fts host only: 8 pgbench clients
   inserting single-row autocommit documents for 120 s while 4 clients run the rare k10
   query, with `fts_merge` every 30 s; reported: insert tps, query tps, and that the index
   count equals the heap count afterwards (the correctness condition the release fixed).
   Release arm only; 39b6a42 is not timed on it because it can lose rows under exactly this
   load (CHANGELOG 1.11.0, "Fixed (concurrency)").

## Comparisons that will be made

- Release vs 39b6a42: per band, with each arm's 3-pass spread; a difference is reported only
  if the spreads do not overlap.
- pg_fts 1.11.0 vs each competitor, per band, as the Approach A tables.
- This run's competitor numbers vs RESULTS_A's: reported as drift for pg_textsearch and
  VectorChord (same versions), as a version change for pg_search.

## What is NOT claimed

As the Approach A and 1.10.0 protocols.  In addition: the concurrent-write band is one
mixed workload on one host; it is not a write-throughput comparison against other engines
(none of them is measured on it).
