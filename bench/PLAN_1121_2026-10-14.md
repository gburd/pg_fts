## Root causes (read in the code)

- **crash, #9, #10 -- `bm25_rescan`.**  It takes `so->query` from `keyData[0]` only, and
  then, when there is an ORDER BY, overwrites it with `orderByData[0]`; no key's
  `SK_ISNULL` is checked.  So a second WHERE key is never applied (#10), a WHERE query that
  differs from the ORDER BY query is replaced by it (#9), and a NULL ORDER BY datum is
  dereferenced (crash).  Every scan reports `xs_recheck = false` for exact queries, so the
  executor never re-applies the lost conditions.
- **#8 -- the boolean evaluator** approximates a phrase/NEAR operand by the AND of its
  terms (a superset; the heap recheck narrows a superset).  Under NOT that superset becomes
  a subset of the true complement, and a recheck can only remove rows.

## Fix (settled against core before coding)

Core semantics checked in the PG 17 source:
- GiST/SP-GiST set `qual_ok = false` for a NULL scan key (the scan returns nothing: the
  operator is strict), and compute a NULL distance for a NULL ORDER BY datum, which the
  executor sorts as NULL (last in ascending order).
- `nodeIndexscan.c` re-applies the original WHERE quals (`indexqualorig`) to every row
  when the AM sets `xs_recheck` -- for ordering scans too (`IndexNextWithReorder`).

1. `bm25_rescan` (crash, #9, #10):
   - any NULL WHERE key: the scan returns no rows (as GiST) -- `so->queryValid = false`
     and no query is dereferenced;
   - NULL ORDER BY key: no ranking query; the scan ranks nothing.  Rows must still come
     back in a defined order with NULL distances, so the scan returns the WHERE query's
     matches (if any) with `xs_orderbynulls` set, i.e. what GiST does;
   - the scan evaluates ONE query (as now: `keyData[0]`, or the ORDER BY query) and sets
     `so->needRecheck` when any other WHERE key exists, or when the WHERE query differs
     from the ORDER BY query.  gettuple/getbitmap then report `xs_recheck = true` (bitmap:
     `recheck`), and the executor applies every original qual.  That fixes #10 (second key
     applied by the executor) and the filter half of #9.
   - #9's other half: an ordering scan must return EVERY row that passes WHERE.  Ranking by
     the ORDER BY query returns only rows that query matches, so a WHERE row the ORDER BY
     query does not reach would be lost (id 2 in #9).  When WHERE differs from ORDER BY,
     the scan candidate set must be the WHERE query's matches, ranked by the ORDER BY
     query's score (0 for a row it does not reach).  Implement by evaluating the WHERE
     query's exact match set and scoring each with `fts_bm25`-equivalent index scoring --
     or, simplest correct form: rank by the ORDER BY query over the full WHERE match set
     via the existing exhaustive path.  Decide after reading `bm25_topk_visible`'s
     candidate admission (the 1.11.0 BoolGate admits by an exact set already).
2. #8: under an odd number of NOTs, a phrase/NEAR operand must be approximated from
   below.  Smallest sound change: in `bm25_eval_query`, a phrase/NEAR evaluated as an AND
   superset under a negation is replaced by the empty set (NOT empty = universe, a
   superset of the true NOT) and the recheck flag is forced; the heap recheck narrows.
   Correct but slow for `x & !"phrase"` (rechecks every x row); PR #12's positional NOT
   evaluation is the fast form and is left for its own review.
