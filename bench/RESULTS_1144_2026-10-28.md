## 3. A2 (`a2/`): measured, not changed

**Corpus and rig.**  2.19M Wikipedia (md5 `f5939e85...`), stored `ftsdoc` column, default
index (104 s build, 1,421 MB, 1 segment), PG 17.10.

**Latency.**  Measured on 1.14.3 and this tree, interleaved, 3 runs each, 6 runs per arm.
Top-10 ids are identical on all six queries.

| query | 1.14.3 | this tree |
|---|---|---|
| `world & war` | 4.600 [4.573-4.614] | 4.569 [4.560-4.588] |
| `film \| music \| album \| band` | 13.704 [13.690-13.781] | 13.684 [13.615-13.847] |
| `united & states` | 1.558 | 1.533 |

The ranges overlap: the changes in this tree do not move the A2 bands.  pg_search was not run
on this rig.  The 1.11.0 comparison (5.87 vs 5.75 ms) was measured on another host and is not
restated here (AGENTS rule 10).

**Offline bound study.**  `a2sim.py` and `a2front.py` count the best-first driver blocks a
`world & war` top-10 visits under each block bound.  `war` is the driver: 2,086 blocks;
`world` has 3,268 blocks; 163,083 documents hold both.

| bound | blocks visited, k=10 | k=100 |
|---|---|---|
| shipped: effective-length bound per term, summed | 643 | 1,843 |
| ROADMAP candidate: pairwise maximum over co-occurring docs only | **642** | 1,843 |
| store the top 1 point of each block's (tf, quantized length) Pareto frontier | 302 | |
| ... the top 2 points | 136 | |
| ... the top 4 points | **55** | |
| ... the top 8 points | 52 | |
| exact per-term block maximum | 52 | 1,250 |
| exact block maximum of the sum (the ideal) | 10 | 96 |

- Every walk returned the exact top-k.
- The pairwise candidate is **refuted** (643 -> 642).
- The loose part is each term's own block bound: it is only 9% loose (median), but the
  k-th score sits on a flat plateau.
- Storing the top 4 frontier points per block is a block-header format change (dual-read,
  a per-segment flag, rewrite on merge; RELEASING.md).  Frontier size: median 6 points,
  p90 8.
- The 4-term OR was not simulated.

## 4. A1 (`a1/`): measured, not changed

The 2.19M stored-column build on this host (8 workers, `maintenance_work_mem` 8 GB) took
103.1 s and 102.6 s.  The DEBUG1 merge timings break that down as:
- the parallel heap scan into 7 worker segments: about 40 s, the remainder;
- the single-backend collapse merge: 39.8 / 39.3 s;
- the in-build pack, a second full merge of the one segment: 23.7 / 23.5 s.

The redesign in the ROADMAP (a shared tuplesort, so the leader writes one segment) would
remove about 63 s of 103.  It is a design change for its own release.

## 5. M2: relevance (`m2/`)

BEIR test qrels, one PG 17.10 cluster:
- pg_fts on this tree, with an English-stemmed column (`d`) and a `simple` column (`ds`);
- pg_search 0.26.1 (ParadeDB deb, default tokenizer, a `bm25` index on id/title/body,
  queried with `paradedb.match` on title and body);
- built-in `ts_rank` over a `to_tsvector('english')` GIN index.

Each query is reduced to its alphanumeric words, ORed together, top 100.

| dataset (queries) | pg_fts english | pg_fts simple | pg_search 0.26.1 | ts_rank |
|---|---|---|---|---|
| SciFact (300), NDCG@10 | **0.6848** | 0.6650 | 0.6339 | 0.5684 |
| SciFact, Recall@100 | **0.9226** | 0.8842 | 0.8909 | 0.8489 |
| NFCorpus (323), NDCG@10 | **0.3240** | 0.3016 | 0.3000 | 0.3001 |
| NFCorpus, Recall@100 | **0.2463** | 0.2340 | 0.2395 | 0.2337 |

- These are not compared with published BEIR figures: none were checked against the
  paper for this file.
- Stemming is worth 0.020 / 0.022 NDCG@10 to pg_fts on these two sets.
- pg_search, which does not stem by default, is below both pg_fts configurations.
- The first SciFact run (`ndcg_scifact.v0_unquoted.jsonl`) was invalid: 68 of 300 pg_fts
  queries failed because a bare `and`/`or`/`not` in the query text is a keyword operator in
  the ftsquery grammar (README).  The harness now quotes each word.  pg_search and ts_rank
  were not re-run: both reported 0 errors, `to_tsquery('english', 'and | or | not |
  auditory')` drops the stopwords (`'auditori'`), and `paradedb.match` takes plain text.
- Two datasets is a small sample.
