## 2. Reviews (I4, `data_150_2026-10-29/review/`)

Two independent read-only sub-agent reviews worked against RELEASING.md's storage / WAL / crash
checklist.

**Review 1** covered v1.14.3..5a01219 and found:
- a blocker: I9's fallback cut could split a UTF-8 character, which raised "invalid byte sequence
  for encoding UTF8" on PG 17/18 with a UTF-8 ctype (a whitespace-free CJK run);
- that I9 chunked every text over 16 kB, so an HTML tag with spaces could straddle a cut.

Both were reproduced before fixing:
- the CJK cut: a new t/004 case fails 2 of 18 on 5a01219 (PG 17.10 and 18.6);
- the HTML tag: tag words were indexed at 31 of 61 offsets near byte 16,383 (0 on 1.14.3).

The fix (2e68acd) parses the whole text first and only re-parses in chunks past the cap,
cutting at whole characters.

**Review 2** (5a01219..2cd5747) found three more problems, all fixed in e50ff1a:
- the discarded first parse leaked its lexemes;
- a new CI step's `make clean` deleted regression.diffs before they could be shown;
- the whole-parse path had no regression test.  The new long_positions case gives 0 tag words
  and 1 doclen shape, the same as 1.14.3; 5a01219 gave 5 and 2.

A human reviewer remains open (ROADMAP I4).

## 3. I3: a compute/storage-separated backend, and redo checked byte-for-byte (`data_150_2026-10-29/i3/`)

**Neon** (built from source, fa504217c, its PostgreSQL 17.5), pg_fts 1.15.0:
- The compute had `shared_buffers = 16MB` and `neon.file_cache_size_limit = 0`, so evicted index
  pages are rebuilt by the pageserver from WAL.  The table has 200k documents, with a stored
  `positions = on` index and an expression `doclen_sidecar = off` index.
- At each of six stages, six query shapes x 2 index forms gave index count = seq-scan count:
  built; deleted + VACUUM; 30k inline-flushed inserts (7 segments); `fts_merge`; `fts_vacuum`;
  a compute restart (every page from the pageserver).  The ranked top-20 matched an `fts_bm25`
  oracle at every stage.
- A branch at an LSN recorded right after the build saw the index as it was then: `rare` 4,000
  rows heap = index = expression, all six shapes equal, ranked top-20 = oracle.  The branch took
  500 inserts + `fts_merge` + VACUUM, which main did not see (0).
- The pageserver logged 0 walredo errors.

**Vanilla, `wal_consistency_checking = 'generic'`**: a primary plus a streaming hot standby, on
PG 17.10 and PG 18.6.
- Workload on the primary: the whole installcheck (34 ok), then a churn of a 200k-row build,
  deletes, VACUUM, 30k inline flushes, fts_merge and fts_vacuum.
- The standby replayed it all with 0 inconsistent pages and 0 FATAL/PANIC, and its index equals
  its heap (> 0).
- The check really ran: one PG17 churn wrote 10,866 Generic records carrying 20,536 images kept
  only for verification ("for WAL verification", pg_waldump).
- A negative control (one bit flipped on the primary's metapage) did not fire, and could not
  have: the next write after a checkpoint carries a full-page write, so the standby receives the
  primary's (corrupted) page and both copies agree.  That is PostgreSQL's design, not a gap in
  the check.

Aurora is not tested: it is closed, and does not run custom C extensions.
