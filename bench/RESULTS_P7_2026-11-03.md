# jimdawdy-hub 7d347ff's scan-path ideas, measured one at a time (2026-11-03)

**Current.**  The four ideas from jimdawdy-hub/pg_fts commit 7d347ff (2026-09-24, "scan path
speedups") that still apply to main, each measured alone against main.  The fifth idea,
append-then-sort for pending matches, has been upstream since 1.13.0.  Raw log, script and
the four patches are in `data_p7_2026-11-03/`.

**Verdict: none is worth porting.**  Three are inside the noise, and one is measurably slower.

## The four patches

Each is applied alone on top of main fbfdb10 (its C code is identical to 29397dc):

| patch | change | path it touches |
|---|---|---|
| p1 | `tidset_sort_uniq` checks whether the input is already sorted and skips the sort if so | collect path: prefix / phrase / count / bitmap |
| p2 | one dictionary lookup per (term, segment) instead of two, in `bm25_topk_candidates_range` | ranked setup |
| p3 | the cursor's block buffer is allocated once (`BLCKSZ`) and reused across blocks, instead of a palloc + pfree per 128-posting block | every WAND and best-first block |
| p4 | one heap slot for the whole visibility loop, instead of create + drop per candidate | every ranked query |

## Method

- **Host:** c6id.metal, PG 18.6, turbo off, server pinned to node 0 cores 8-15, psql on cores 16-17.
- **Corpus:** 640k rows of 60 tokens each, log-uniform over `t1..t5000`, one segment.
- **Builds:** one index; the `.so` swapped among base, base2 (A/A, the same tree built twice), p1, p2, p3 and p4.
- **Timing:** 6 ABBA rounds, 12 samples per build.  Each sample is the median of 11 runs after 3 warm-up runs.
- **Correctness:** all 11 shapes return identical ids, or an identical count, on all five builds.

## Per patch

- **p1 (presorted check): slower, do not port.**
  - **Bitmap count:** +5.0%, and its range does not overlap base's at all.
  - **Why, from the code:** the prefix leaf (`bm25_lookup_prefix`) appends each matching term's postings in turn.  Each run is sorted, but their concatenation is not.  So the check scans up to the first inversion and then sorts anyway: pure added work.
  - **Not separated:** this count's other `tidset_sort_uniq` calls (on the AND result and on the accumulated set) were not timed one by one.
  - **Ranked rows:** within noise.
- **p2 (one dictionary lookup):** -2.0% on `t10 | t11` top-10, -1.1% on a 4-term OR top-10, but +1.6% on the 3-term rare OR.  The ranges overlap base on all of them.  It saves one in-memory dictionary-index lookup per (term, segment): about 1 us on a multi-ms query.  **NOISY, no claim.**
- **p3 (block-buffer reuse):** between -1.0% and +1.5%, inside the A/A spread of up to 0.6% plus build-to-build layout noise.  PostgreSQL's allocator already recycles a freed chunk of the same size, so palloc + pfree per block costs little.  **No effect.**
- **p4 (one heap slot):** every row within 0.25% of base.  **No effect.**

## Not measured

- **The multi-segment case for p2.** A stable 8-segment index could not be built: inline flushes trigger the level-0 compactor, and VACUUM's cleanup packs.  p2's saving grows with the number of segments, but it is a lookup per segment, not per posting.
